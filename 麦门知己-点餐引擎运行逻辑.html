00一条铁律

规则负责"想"和"算"，模型负责"说"和"看"。
模型没有选品权，没有定价权，没有改单权。它可以判断、可以说话， 但所有落地的动作都必须回到本地代码的白名单里执行。

这条铁律决定了整棵树长什么样：凡是需要确定性的地方（价格、份数、编码）， 一律走规则；凡是规则写不出来的地方（这句话够不够清楚、这份菜单像不像人点的）， 才交给模型 —— 而且只让它输出判断，不让它输出结果。

能力归属为什么
判一句话清不清晰模型正则写不出"这句话够不够我直接选品"，但模型能
抽忌口 / 人数 / 预算模型 + 规则并集模型会漏，忌口漏一个是安全事故，规则必须兜住
从记忆和时间推方向模型要把"很烦"翻译成"重口/脆的/带辣的"，这活儿规则干不了
挑哪个商品、配几份规则必须可复现。同样输入 100 次结果一致，演示绝不翻车
判断这单合不合理模型"一个人四个主食"这种常识，规则穷举不完
执行纠偏本地白名单模型只说"删第 2 项"，删不删、怎么删由代码定
价格 / 份数 / 商品编码规则钱的事一个字都不能让模型碰
写开场白和收尾金句模型这是模型唯一有创作自由的地方

01全局树状图

从下往上看不方便，从上往下看这棵树的形状：主干只有一条， 但沿途有四个地方真正分叉 —— 分叉出去的支路要么自己走完返回、要么汇回主干。 看见分叉就知道"这里做了个决定"。

模型判断 规则计算 真实数据 落盘 / 同步 出口 / 决策点
怎么读这棵树：主干从「用户说一句话」一路向下，中间只有两条线会离开主干再回来—— 左边那条是旁路（模糊时替用户补全），右边那条红虚线是重配回环（判断说这单不像话时， 带着"要避开的商品"退回选品重来）。其余全是主干上的串行步骤。

02分叉一：这句话够不够清楚

这是整棵树最开始、也最关键的一个判断。判定权完全交给模型，规则不再说话。

为什么这一刀必须让模型来切：旧版是规则靠「有没有 people / budget / taboo / taste」推"够不够清楚"， 结果两头都错 ——
· 「今天好烦」因为句子里有"今天"（被当成时间约束）被判成清楚，直接硬选品，选出来全靠规则瞎猜；
· 「帮我点个午餐」因为什么约束都没有被判成模糊，于是反问「想吃带劲的还是舒服的」—— 用户已经说要吃饭了，还问他要哪种感觉。

新口径只有一句话：光靠这句原话，能不能直接在菜单上挑出东西。挑得出来就是 clear，挑不出来就是 vague。

vague · 走旁路

特征：只有状态或态度，没有可选品条件

「今天很烦」　「心情不错」

「帮我点个午餐」　「我饿了」

「随便」「吃点什么好」

去哪：→ 分叉二，旁路替用户补全

clear · 直接进主循环

特征：说了具体约束，能直接选品

「我要吃辣的」　口味

「3 个人 50 块」　人数 + 预算

「花生过敏」　硬忌口

去哪：→ 跳过旁路，直接第 ② 步查菜单

硬约束 → 强制 clear（防模型手滑的兜底）

模型再准也会抽风。所以代码里有一道单向强制：只要用户明说了忌口 / 人数 / 预算， 就算模型判 vague，也一律拉回 clear。

// llm-intent.service.ts · mergeIntent
// 有明确约束就直接进选品，这是我们能百分百确定的
if (taboo.length > 0 || explicit.budget !== undefined || explicit.people !== undefined) {
  clarity = 'clear';
}

理由很实在：用户写了「花生过敏」，模型要是判 vague，白跑一趟旁路不说，旁路还有可能把忌口弄丢。 忌口漏判是吃出问题的事，不能赌。

忌口为什么是「模型 + 规则取并集」

这一处是唯一不由模型单独说了算的字段。合并规则：

情况处理原因
模型漏了忌口，规则抽到了并集收下漏一个就是安全事故，规则必须捞回来
模型提了新忌口，原文里有「不吃 / 过敏 / 别放」收下模型补上了规则没覆盖的说法
模型把口味写成忌口（原文没有否定词）丢弃用户说"想吃辣"，模型写 taboo:["辣"]，采信会把整个辣味菜单清空 —— 比漏判更糟
口味与忌口重叠口味让位忌口是硬约束，优先级更高
真实日志：模型给的忌口「辣」原文里找不到依据，已丢弃

03分叉二：旁路 —— 模糊不等于反问

用户说「今天很烦」时，系统有两条路可走：把问题问回去，或者自己替他想。这里选了后者。

旁路的产物不是菜单，是一份「判断结论」。
它只产出方向标签（辣 / 热 / 大份）、推定人数、该避开的商品，然后并入 intent， 交给确定性的选品引擎去真实菜单里落地。所以"模糊"不会变成"再问一遍用户"，而是变成"系统替你多想了想"。

旁路拿到什么

输入一：你的记忆

  • 忌口 / 过敏（绝对不能沾）
  • 口味标签、常点单品、特制习惯
  • 历史预算区间
  • 最近几天的情绪记录

输入二：当下的时间事实

  • 时:分 + 星期几
  • 时段（早餐 / 午餐 / 下午茶 / 夜市 / 深夜）
  • 节气 + 它的意境描述
  • 是否在水逆期间、第几天

时间事实由编排器算好后传进去，不是让模型自己猜今天几号 —— 保证和主链路用的是同一个时间。

输出之后怎么合并：只填空，不覆盖

字段合并方式为什么
口味倾向并集，但先规范化模型爱说「解压」「省事」，选品引擎不认这些词，得先翻译成「辣」「大份」
人数只填空用户说了 5 人，绝不能用旁路猜的 2 人
情绪意图没结论才用旁路的情绪策略直接影响选品打分
预算永远不进显式约束见下方红框
踩过的坑：旁路推的预算不能当"用户说的预算"。
记忆里存着预算区间 [46.28, 87.5]，旁路很自然会填 budget = 87.5。 但 explicit.budget 的语义是"用户说了这个数"，它会导致三件事： ① 回复卡片上冒出一条预算进度条；② 触发超预算重选；③ 落进记忆当成事实。
而模型每次推的数还不一样（实测同一句话推出过 87 / 88 / 87.5 三个版本）， 于是同一句话每次点出来的菜单都不同。现在它只进 softBudget，纯参考，不当墙。

口味词怎么翻译（这段代码不显眼但很关键）

// 模型的语言 → 引擎的语言
解压 → 辣 + 大份　　省事 → 大份　　暖胃 → 热
提神 → 咖啡　　　　重口 → 辣　　　

// 认不出来的一律丢掉，不留成噪声

不做这一步的后果是静默失效：标签对不上不会报错，只是选品一个字都没听进去 —— 模型说了半天，菜单毫无变化，而日志里看起来一切正常。

04分叉三：出单判断（三档）

菜单配好之后、算价之前，请模型看一眼：这份单像不像人真正会点的。 结论分三档，每档对应一个明确的本地动作。

模型这次能输出什么、不能输出什么

字段说明本地怎么处理
severitynone / minor / major决定走哪一档，但必须自洽（见下方降级规则）
remove要删的序号，如 [1,3]越界一律忽略，绝不误删
avoid只在 major 时填，必须原样抄菜单上的名字对不上菜单的当建议句丢掉
为什么只要序号，不要商品编码。早期让模型输出嵌套的 {kind, fix, index} 对象， 它经常把 issues 写成字符串数组、把 fix 字段漏掉，整条复核对不上任何动作，等于白跑。 现在只要一个数字数组，稳定得多 —— 而且从根上不给它机会返回商品编码。

三道自洽性降级

  1. 说 major 但既给不出 avoid 也给不出 remove → 降成 none。否则会触发一次"不知道为什么重配"的重选，白烧额度还可能配得更乱。
  2. 说 major 但 avoid 为空 → 降成 minor，只做减法。
  3. 纠偏会把菜单清空 → 放弃本次纠偏。用户拿到空菜单比拿到一份略多的菜单更糟。
真实日志：复核判 minor：一个人两个主食，过量了 | 删 #2
执行：删除 #2 麦乐鸡开心乐园餐（remove_extra_main）　→　¥64.00 变成 ¥39.40

注意 major 的重配也不让模型选品：它只交出"最该换掉的 1-2 个名字"， 规则拿着这个名字回候选池做降权（降到负分），再重新组单。 视频演示里如果重配结果和原来完全一样，会退化成 prune，不会无限循环 —— 只跑一次。

05分叉四：购物车结论怎么用

判断环节除了看"这一单"，还要看"车里现在有什么"。但这两者的关系语义必须先讲清楚，否则模型会给出一堆无效建议。

关键前提：主循环出单是「整份替换」购物车。不是追加。 所以车里现有的东西代表的是用户上一轮拿到、并且可能手动调过的结果 —— 它的价值不在于"去重"，而在于它记录了用户的编辑痕迹。

为什么「用户删了什么」必须单独检测

上一轮系统给的是「麦辣鸡腿堡套餐 + 薯条 + 可乐」，用户手动把薯条删了。
这一轮他说「来点辣的」—— 如果系统不看购物车，会重新配一份含薯条的菜单，整份替换购物车。
用户的删除操作被无声抹掉，ta 会觉得"我删的东西你怎么又给我加回来了"。

所以代码里有一处专门的检测：读 chats 表里最近一条 reply_json， 拿上一轮的菜单和现在的购物车对比，少掉的那些就认定为用户主动删除，转成选品时的降权名单。

为什么要拿上一轮的单来比：购物车里只有"现在有什么"，没有"本来有什么"。 少的那一样到底是用户删的、还是上一轮本来就没有 —— 必须和上一轮对比才知道。 而且策略很保守：只要对不上名字就当没这回事，不猜。

反过来，模型这边要明确禁止它去建议删车里的东西 —— 本地白名单只认这一单的下标，越界直接忽略， 它的建议会变成无效动作，白烧几百毫秒。

06查真实菜单

这一步是整条链路上唯一的数据来源。没有它，后面所有环节都是编的。

查什么接口失败怎么办
门店query-nearby-stores（只接受「城市 + 关键词」）缺定位就如实报 NeedLocation，不猜
商品query-store-menu空列表直接报错，不给假菜单
优惠券query-coupons静默失败，不影响出单
营养query-nutrition静默失败，不影响出单
到店和外送是两套商品编码。实测同一门店 88 个到店编码里，有 75 个在外送侧不存在。 所以履约方式必须在对话开始时就定下来，选品、算价、下单全链路按对应场景走 —— 中途切换会导致菜单里的商品根本下不了单。

07选品打分

确定性打分，同一输入 100 次结果完全一致。这是"演示绝不翻车"的地基。

加分项

权重条件
+5套餐份数正好匹配人数（双人餐配 2 人）
+4命中用户明说的口味
+3命中节气关键词 / 用户本命单品
+2口味匹配当前情绪策略、命中特制习惯、套餐自带饮料或小食
+1价格落在平时的价位区间

减分项

权重条件
−4用户说要减肥，这个是高热量
−5命中当前情绪该避开的东西
−6根本不是吃的（调味酱 / 周边 / 毛绒）
−100命中忌口 —— 直接出局
套装自带的东西要"记账"。麦辣鸡腿堡套餐里本来就有可乐和薯条。 如果不把这份套餐自带的饮料/小食算进结构额度，系统会认为"还欠一杯饮料 + 一份小食"， 紧接着补上无糖可乐和麦乐鸡 —— 一个人一餐两杯饮料两份小食。 这是"套餐配了饮料又点一杯"的根因。

人数：没说就按 1 个人

优先级是用户明说 > 旁路推断 > 默认 1 人。没说人数就一个人，不给"你是不是两个人吃"这种反问。

「两个汉堡」是量词不是人数。早期只认"数字 + 个/位/人"， 「两个汉堡一杯可乐」被判成 2 人，系统按 2 人份配菜 —— 用户一个人吃，收到双份主食。 现在「个」后面紧跟食物名就跳过。

记忆里的忌口要给当轮原话让位

真实踩到的：记忆里记着「忌辣」，这一轮用户说「我要吃辣的」。
两边都当真 → 选品因为 taste=辣 挑了一份龙焰鸡腿堡，文案却写 「辣的我得拦一下 —— 你忌辣这事儿我记着」。一边给一边拦，用户直接懵。

规则：当轮原话 > 历史记忆。但只让「口味型忌口」让位（辣 / 甜 / 冰 / 咖啡…）， 过敏源永远不让 —— 花生、坚果、海鲜不在口味词表里，永远不会被摘掉。安全优先于顺从。

08算价与文案

④ 算价（纯规则）

小计 → 优惠券抵扣 → 外送费 + 打包费 → 营养估算

价格永远来自真实数据，模型碰不到。

套餐价与单点价要按 MCP 返回的实际情况取，不能自己算。

⑤ 文案生成（模型唯一自由区）

只输出两个字段：{hook, quote}

开场 2-3 句，要点明推荐的具体依据（节气 / 星座 / 记忆 / 情绪）。

收尾 1-2 句，要有一句能让人截图的话。

文案层的硬禁止

  • "亲爱的用户""您好""以下是为您推荐" —— 像客服，不像朋友
  • 编造任何商品名、价格、优惠、热量
  • 输出菜单结构 —— 菜单已经由系统生成好了，它不需要也没资格输出
  • markdown 语法、列表符号、emoji 堆砌
安全模式开启时，所有这些玩法全部禁用。禁节气、禁星座、禁水逆、禁话术技巧。 用平实的语言，像一个真正关心人的朋友。可以说"我在"，不要说"我懂你"——你其实不懂。

09落盘与同步

最后一步是两个并行的写操作，它们互不阻塞。

写 chats 表

  • 用户原话、回复全文、菜单快照
  • 标记 clarifyOnly：这一轮是不是只问了句话
  • 下轮判断"上次是不是刚反问了"就靠它

整份替换购物车

  • 按 (user_id, fulfillment) 存一份
  • 到店和外送分开存 —— 编码是两套，混着放必然串场
  • 价格存单价，小计永远现算
为什么价格存单价而不是小计：用户改数量时，存小计会算错。 合计（含外送费）永远现算 —— 用户看到的"合计"必须是最终付款金额，不是商品价之和。

10真实对话轨迹

案例一：模糊意图「今天很烦」

跑旁路不反问

流水线：intent → context → menu → review → compose
旁路  ：✅ 跑了
反问  ：✅ 没有，直接给了菜单

门店：麦当劳厦门鹭港万达餐厅 · 午餐
标题：你的「水逆急救单」
菜单：
  吉士汉堡包套餐 ×1  ¥26.5   — 应季（汉堡），你想吃的（大份），套餐自带饮料和小食
  新地            ×1  ¥12.5  — 应季（新地），你的本命（草莓新地）
  麦乐鸡开心乐园餐 ×1  ¥25.0  — 在你平时的价位
合计：¥64.00

开场：烦就烦吧，霜降这天本来就不该顺。**水逆第 4 天**，锅真不是你的。
      我按摩羯的老规矩给你配的——不冒险、够大份、算得过账。

案例二：明确意图「我要吃辣的」

跳过旁路判断环节生效

流水线：intent → menu → review → compose   （没有 context，正确跳过）
意图  ：clear · taste=[辣] · "给出明确辣味约束，可直接选品"
判断  ：minor「一个人两个主食，过量了」→ 删 #2 麦乐鸡开心乐园餐
结果  ：¥64.00 → ¥39.40
这一对的对照意义：同一套代码，模糊时多绕一条旁路、明确时少绕一条， 而两条路最终都汇进同一个主循环，都能拿到完整菜单。这就是分叉设计要验证的东西。

11失败降级表

每一层都可能挂，任何一层挂掉都不能让用户白屏。

哪一层挂了降级到哪用户看到什么
意图解析模型超时规则解析 + 规则判 clarity照常点餐，只是判断粗一点
旁路模型挂了1 人 + 无倾向，直接选品菜单朴素一点，但仍然有
判断环节挂了按"没发现问题"处理菜单照出，只是没做二次体检

唯一不降级的地方是"真实数据"。门店和商品查不到，必须如实报错。 给一份编出来的菜单，比报错更伤 —— 用户点了下不了单，还以为是系统在骗他。

12为什么这样分工

1. 为什么不让模型直接选品

因为价格和编码必须是真的。模型不知道今天这家店哪几样还热着、哪个编码下得了单。 它一旦编一个商品名，用户点下去就失败 —— 而且失败的原因用户永远搞不清。

反过来，规则选品是可复现的：同样输入 100 次得到同一份菜单，演示不会翻车，出了问题能定位到具体哪一条打分。

2. 为什么意图解析反而要交给模型

因为"这句话够不够清楚"这件事，正则写不出来。 「今天好烦」和「今天想吃辣的」字面结构几乎一样，但一个该走旁路、一个该直接选品。 只有理解语义才能分开。这一刀让模型切，是整次重构最大的收益。

3. 为什么规则不能退休

三个理由：

  • 忌口是安全事故。模型漏一个就是吃出问题，规则必须能捞回来，所以取并集而不取交集。
  • 中文数字和预算说法有十几种（「仨」「两位」「一百以内」「预算八十」），正则可复现、可单测、零成本。
  • 模型会挂。必须有降级路径让用户还能点餐，而这条路径只能是规则。

所以规则的角色从"决策者"降级成了"约束抽取器 + 兜底"—— 它不再决定"这句话清不清晰"，但它守着安全线。

4. 为什么判断要放在算价之前

因为判断可能会删东西（prune）甚至换一单（rebuild）。 如果先算价再判断，删完就得重算一遍，等于算两次；而算价里有优惠券核销， 重算可能拿到不同的券 —— 价格会跳。

5. 为什么旁路只在模糊时跑

用户说「3 个人 50 块」的时候，该给的信息都给了。 这时候还去分析"他今天心情怎么样、现在几点"，除了拖慢 2-4 秒、多烧一次调用之外没有任何收益 —— 而且推出来的结论还会干扰已经明确的约束。

一句话总结这棵树：主干是确定的（数据 → 规则 → 算价）， 四个分叉是判断的（清不清晰 / 往哪个方向 / 合不合理 / 车里有什么）， 而所有判断的执行权始终留在本地代码手里。
