## 能做什么

### 场景① 情绪输入：「我好烦啊」

用户只说了「被客户烦的不行」——没给人数、没给预算、没说要吃什么。
（就是开头那张图。）

```
你：我好烦啊

它：收到。水逆第 3 天（我记得，你 22 号就开始跟我抱怨代码了），
    霜降刚过一天，天一冷人就容易烦——这是宇宙的锅，不是你的。
    对了，明天就是你生日，天蝎座寿星本周宜甜食续命。我给你安排了：

    ── 你的「水逆急救单」· 留仙洞店 ──
    新地（巧克力）    ×1                甜度抵消 30% 烦躁         ¥11.5
    麦辣鸡翅          ×2                烦就要吃辣，物理发泄       ¥16.0
    冰鲜柠檬水        去冰 · 你上次说的   霜降了还是留了点冰的自由    ¥9.5
    热可可            ×1                霜降限定情绪，热乎的才对    ¥13.0

    券后实付 ¥39.5  原价 ¥50.0                    热量 ≈ 720 kcal

    "宇宙没善待你，但优惠券有。上周四你烦的时候吃了麦麦鸡说治愈
     ——这次加个热可可，霜降嘛，麦门。"
```

它做了这些事：识别情绪 → 查节气（霜降）→ 查水逆（第 3 天）→ 查生日（明天）→
读记忆（怕你烦躁、可乐去冰）→ 按情绪策略选品（烦躁→甜+辣+冰）→ 排除忌口 → 算券后价。

## 快速开始（本地跑，5 步）

### 1. 环境要求

- **Node.js ≥ 22**（用了内置 `node:sqlite`，编译零依赖）
- 一个麦当劳 MCP Token：打开 [open.mcd.cn](https://open.mcd.cn) 扫码登录 → 控制台激活 → 复制 Token

### 1.1 MCP 怎么配

仓库根目录的 [`mcp-config.example.json`](mcp-config.example.json) 是 MCP 连接配置示例，
所有凭证都用环境变量占位符（`${MCD_MCP_TOKEN}`），文件里没有任何真实 Token。

**两种用法，注意区分：**

**① 在 WorkBuddy / Claude 等 MCP 宿主里直接跑（推荐用于体验 MCP 能力）**

把示例里的占位符换成本机环境变量名，粘进宿主的连接器配置即可：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": { "Authorization": "Bearer ${MCD_MCP_TOKEN}" }
    }
  }
}
```

**② 跑本项目（Token 不进配置文件）**

本项目**不需要**把 Token 写进 `mcp-config.example.json`。
架构上 Token 由用户登录时粘贴一次，服务端用 AES-256-GCM 加密落库，
每次调用前在内存解密再注入请求头（见 `server/src/mcp/gateway.ts`）。

所以你只需要在 `server/.env` 里配端点：

```bash
MCP_ENDPOINT=https://mcp.mcd.cn
```

然后启动服务，在浏览器里粘贴 Token。

> ⚠️ `mcp-config.example.json` 是**给人参考格式**的，服务不会读它。
> 真要跑本项目，改的是 `server/.env`。

### 2. 拉代码装依赖

```bash
git clone <your-repo-url> mcd-soulmate
cd mcd-soulmate
```

前后端依赖分开装（两端各自独立）：

```bash
cd server && npm install
cd ../web && npm install
```

### 3. 配置环境变量

```bash
cd ../server
cp .env.example .env
```

生成两个必须的密钥并填进 `.env`：

```bash
openssl rand -hex 32   # → 填给 JWT_SECRET
openssl rand -hex 32   # → 填给 TOKEN_ENC_KEY（必须是 64 位 hex）
```

`LLM_API_KEY` 可以留空 —— 留空时回复走内置模板，功能完整只是文案没那么灵动。

### 4. 构建并启动

先构建前端（产物落在 `web/dist`，服务端会自动托管它）：

```bash
cd ../web && npm run build
```

再构建并启动后端：

```bash
cd ../server
npm run build
npm start
```

看到这两行就成功了：

```
静态前端：/path/to/mcd-soulmate/web/dist
✅ 麦门知己后端已启动 http://localhost:3000
```

### 5. 打开浏览器

访问 **http://localhost:3000** → 粘贴你的 Token → 开始聊。

> 后端开发模式用 `npm run dev`（tsx watch，改代码自动重启）。
> 前端开发模式另开一个终端 `cd web && npm run dev`（Vite HMR，默认 5173 端口，已配好 API 代理）。

### 只想看看界面，不想配 Token？

前端内置了一套 mock 数据层，加上 `?mock=1` 就能不连后端走完三个场景：

```bash
cd web && npm run dev
# 打开 http://localhost:5173/?mock=1
```

mock 模式下任意 20 位以上的字符串都能登录（不校验 Token 格式）。

> ⚠️ 不能直接用 `python -m http.server` 打开 `web/index.html` ——
> 那是 Vite 的源码入口，引用的是 `/src/main.ts`，必须经过 Vite 处理才能跑。

## 部署到自己的服务器

目标：单台 Linux 服务器，单进程，零外部 SaaS 依赖。

### 前置

```bash
# Node 22
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx sqlite3

# pm2
sudo npm i -g pm2
```

### 第 1 步：放代码 + 配置

```bash
sudo mkdir -p /var/www/mcd-soulmate
sudo chown -R $USER:$USER /var/www/mcd-soulmate
git clone <your-repo-url> /var/www/mcd-soulmate
cd /var/www/mcd-soulmate/server

cp .env.example .env
# 填 JWT_SECRET / TOKEN_ENC_KEY / LLM_API_KEY，并把 NODE_ENV 改为 production
chmod 600 .env          # 重要：别让同机器上其他用户读到
```

### 第 2 步：自检

```bash
bash ../scripts/preflight.sh
```

会输出一份 ✅/❌ 清单：Node 版本、密钥格式、数据目录权限、端口占用、MCP 连通性、构建产物。
**全部 ✅ 再继续。**

### 第 3 步：构建 + 启动

```bash
npm ci && npm run build
pm2 start ecosystem.config.js
pm2 startup         # 按提示执行它输出的那行 sudo 命令
pm2 save            # 保存进程列表，服务器重启后自动恢复
```

> ⚠️ `ecosystem.config.js` 里 `instances` 必须是 **1**。
> SQLite 单文件写锁 + 内存连接池都是进程内状态，开 cluster 多实例会互相踩
> （订单幂等失效、连接池重复建连、限流计数不准）。

### 第 4 步：Nginx

```bash
sudo cp ../nginx/mcd-soulmate.conf /etc/nginx/sites-available/mcd-soulmate.conf
sudo nano /etc/nginx/sites-available/mcd-soulmate.conf   # 改 your-domain.com 和路径
sudo ln -s /etc/nginx/sites-available/mcd-soulmate.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

**SSE 必须关缓冲**，否则流式回复会卡住一次性蹦出来。配置里已经写好了：

```nginx
location /api/ {
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 120s;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
    gzip off;
}
```

### 第 5 步：HTTPS

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d your-domain.com
```

certbot 会自动改写 nginx 配置并配好续期。验证续期：`sudo certbot renew --dry-run`

> **全站 HTTPS 是部署红线** —— Cookie 里是会话凭证，走 HTTP 会明文泄露。

### 第 6 步：备份 cron

```bash
crontab -e
```

```cron
# 每日 3:00 备份（注意 % 必须转义为 \%）
0 3 * * * bash /var/www/mcd-soulmate/scripts/backup.sh >> /var/www/mcd-soulmate/logs/backup.log 2>&1
```

手动验证一次：

```bash
bash /var/www/mcd-soulmate/scripts/backup.sh
```

输出里有 `integrity_check = ok` 就对了。

> 💡 **为什么不能直接 `cp mcd.db`**：服务运行时 WAL 有未落盘数据，
> 直接拷贝会拿到不一致的快照。脚本用的是 `sqlite3 .backup`（官方在线备份 API）。

### 第 7 步：后续更新

```bash
bash /var/www/mcd-soulmate/scripts/deploy.sh
```

幂等脚本：拉代码 → 装依赖 → 构建 → `pm2 reload`（零停机）→ 健康检查。
失败会在对应步骤退出并打印日志。

```bash
bash scripts/deploy.sh --with-preflight   # 首次部署建议带上自检
bash scripts/deploy.sh --no-pull          # 只重新构建，不拉代码
```

## 点餐路由：它是凭什么这么点的

上面那张图是「系统长什么样」，这一节是「它凭什么这么点」。

观众反馈最集中的就是这个 —— 不是因为它推荐得准，而是因为**每一行菜单背后都有一条能被追问的依据**。
所以这一节按真实代码写，包括几个维度到底参与了多少：有的决定选什么，有的只决定怎么说。

### 0. 一句话版本

> 五个维度单独看都很轻（+2 到 +4 分），但它们是**叠加**的。
> 一条商品同时命中"应季 + 本命 + 对情绪有用 + 你平时价位"，就从 0 分变成 10 分。
> **没有哪个维度能单独决定菜单，但一起决定的时候，菜单就长得很像"有人替你想着"。**

### 1. 五个维度，先分清哪些真的在选品

这是整节最需要说清的一件事。五个维度不都是"打分项"：

| 维度 | 数据来源 | 在选品里的权重 | 主要作用 |
|---|---|---|---|
| **节气** | 24 个节气静态表 | **+3**（命中 keywords） | **选品** + 文案 |
| **情绪策略** | 6 类情绪静态表 | **+2** / **−5**（命中 tasteStrategy / avoid） | **选品** + 语气温度 |
| **星座** | 12 星座静态表 | 0 | 文案（生日月另算） |
| **水逆** | 7 段静态区间（2026–2027） | 0 | 文案 |
| **时段** | 小时数直接判定 | 0 | 文案 + 反问措辞 |

**实话实说**：表里权重为 `0` 的三个维度（星座 / 水逆 / 时段）**完全不进打分函数**
—— `selectProducts()` 的入参里只有 `strategy`（节气）和 `moodStrategy`（情绪），
拿不到星座和水逆。它们影响的是"这单怎么被说出来"，而这件事在体验里同样重要，
因为用户记住的往往是那句话。把两者混着讲会更好听，但经不起细看，所以这里分开写。

### 2. 节气：24 个，全年无缝

`server/src/data/solar-terms.ts`，24 条，每条四个字段：

```ts
{
  name: '霜降',
  startMonth: 10, startDay: 23, endMonth: 11, endDay: 6,
  imagery: '秋末昼夜温差大，人要贴秋膘',        // 给 LLM 的画面描述
  strategy: ['温热', '高碳水', '高满足感'],      // 取向标签
  keywords: ['热可可', '板烧', '浓汤', '汉堡', '新地'],  // ← 真正参与打分
  blurb: '霜降是秋天最后一个节气，贴秋膘这事该办了。',   // 可直接用的文案
}
```

只有 `keywords` 进选品。做法很朴素：拿这 5 个词去商品名/分类/描述/配料/套餐明细里找，
命中就 **+3**，理由写成「应季（汉堡）」。命中多个词也只加一次 3 分 —— 不然甜品会靠堆词赢。

日期区间按"月×100+日"比较，支持跨年（冬至 12/22 → 1/4 就是跨年项），所以全年没有空档。

### 3. 情绪：6 类，先看优先级再看"避免什么"

`server/src/data/mood-strategies.ts`。六类情绪各自有 `tasteStrategy`（往上加）和 `avoid`（往下压）：

| 情绪 | 想吃 | 避开 | 语气 |
|---|---|---|---|
| 烦躁 | 甜 / 辣 / 冰 | 清淡、健康说教、轻食沙拉、小份 | 俏皮 |
| 疲惫 | 高碳水 / 热 / 提神 | 复杂选择、需要动手的、轻食 | 正常 |
| 低落 | 温热 / 甜 / 软糯 | **玩梗、嘲讽、说教、星座话术、节气话术**、刺激 | **温和** |
| 开心 | 加料 / 大份 / 分享 | 轻食、小份、克制 | 俏皮 |
| 平淡 | 尝鲜 / 小惊喜 | 重口、太刺激 | 正常 |
| 庆祝 | 仪式感 / 甜品 / 大份 | 轻食、小份、将就 | 俏皮 |

命中 `tasteStrategy` **+2**，命中 `avoid` **−5**。负分绝对值更大，
是因为"推错一样东西"比"少推一样对的东西"更伤 —— 给烦躁的人推轻食沙拉，比什么都不推更让人无语。

情绪识别本身有两条硬规则：

- **负面优先**。`烦躁 > 低落 > 疲惫 > 庆祝 > 开心 > 平淡`。「累死了终于搞定了」判成**疲惫**，不是开心 —— 真实状态是累。
- **反讽优先于正向**。命中 `太好了呢 / 真棒啊 / 好得很 / 呵呵` 这类模式时，
  直接按**烦躁**处理，置信度压到 0.5 —— 「太好了」配个语气词，通常是反着说的。

`低落` 这条是我刻意收紧的：`avoid` 里同时禁了**星座话术和节气话术**。
理由是一个情绪低落的人并不想知道"你天蝎座本周宜甜食"，那听起来像在敷衍。

### 4. 安全模式：一条比选品更硬的规则

`SAFETY_KEYWORDS` 命中（想死、撑不下去、活着没意思、绝望…）时，`safetyMode = true`，
整条链路会切到另一种走法：

```
safetyMode = true
  ├─ 提示词里**关掉话术样本**（strategyToPrompt 的几个 if）
  │    ✗ 节气 blurb（那句"贴秋膘这事该办了"）
  │    ✗ 星座整段、生日月、水逆
  │    ✗ 情绪 sampleHook
  │    ✓ 但节气名/取向/情绪口味取向**照常传** —— 选品还得靠它
  ├─ 跳过旁路分析（clarity 为 vague 也不跑）
  ├─ 跳过反问 —— 不安慰、不追问，直接给菜单
  └─ 系统提示词追加一段硬指令：
       「禁用：节气、星座、水逆、任何话术技巧。
         用平实的语言，像一个真正关心人的朋友。
         不要说"我懂你"，你其实不懂。可以说"我在"。」
```

注意这里的分寸：**不是把知识层整个关掉**，那会让菜单失去依据；
而是**把"说话的技巧"关掉，把"选什么的依据"留着**。用户需要的是一顿合适的饭，
不是一个不敢说话的机器人。

这不是产品修饰，是**功能上把话术关掉**。一个点餐 Agent 在这种时刻最好的表现是少说话、
把饭配好，而不是借机讲一个星座段子。

### 5. 星座 / 水逆 / 时段：不参与选品，但决定"这单像不像人说的"

这三个维度不影响打分，各自有明确落点：

**星座** —— 按生日算，太阳星座区间全年无缝（天蝎座 10/24–11/22，`personality` 是
「爱恨分明，要么清汤要么爆辣」）。它的价值在**生日月**：`isBirthdayMonth()` 为真时，
会往提示词里塞一句 `birthdayTactic`，天蝎座那句是
「生日月圆筒当长寿冰淇淋，简单但够狠」。一句话，但它是"被记住"的证据。

**水逆** —— `mercury-retrograde.ts` 里是 2026/2027 的静态区间。这里有一句诚实的注释：

```ts
/** ⚠️ 演示用静态表，非天文精确。真实水逆每年 3–4 次，每次约 3 周。
 *  数据来源为占星通行区间，仅用于产品叙事，不用于任何计算/预测。 */
```

代码按进度把水逆切成 `start`（前 25%）/ `mid` / `end`（后 20%）三段，
文案只说"第 3 天"这种事实，不预测吉凶。它出现在首屏 hook 里 —— 这是全项目最讨巧的地方：
**一个不承担任何推荐责任、但用户第一眼就会笑一下的信息**。

**时段** —— 五个桶直接按小时切：早餐 5–10、午餐 10–14、下午茶 14–17、夜市 17–22、深夜 22–5。
作用是两处：一是反问文案随时间变（早上问"热的还是清淡好带走的"，深夜问"这么晚了想吃点热的暖一下"），
二是菜单标题那行 `午餐 · 现在取`。

> **一个诚实的遗留项**：`slotToMealPeriod()` 定义了「时段 → MCP 餐段」的映射，
> 但**目前没有任何地方调用它**。真实实现里餐段可用性是靠商品自身 `available` 字段判断的，
> 没有额外按餐段过滤。这行代码是给后续接 `mealPeriod` 参数留的，现在属于死代码 ——
> 与其在 README 里假装它生效了，不如标明。

### 6. 分数怎么变成一张菜单

知道每一项加多少分之后，真正决定菜单的是**怎么把分用起来**。
`selector.service.ts` 的完整打分表：

| 项 | 分 | 说明 |
|---|---|---|
| 命中节气 keywords | **+3** | 应季 |
| 用户本命单品 | **+3** | 记忆里的常点 |
| 口味符合情绪策略 | **+2** | 对情绪有用 |
| 命中用户特制习惯 | **+2** | 你常点的 |
| **命中用户嘴上说的口味** | **+4** | 权重最高，见下 |
| 价格在平时区间 | **+1** | 在你平时的价位 |
| **人数匹配** | **+5 / +2 / +1** | 见下 |
| 单人点的套餐自带饮料 | **+2** | 含饮料就算完整一餐 |
| 单人点的套餐自带小食 | **+1** | 同上 |
| 单人点整餐（vs 单点汉堡） | **+1** | 一份就是一顿 |
| 命中情绪 avoid | **−5** | 此时不合适 |
| 不是吃的（酱/周边） | **−6** | 这不是主餐 |
| 说了减肥/清淡却选重口 | **−4** | 你说要减肥，这个偏重 |
| **忌口命中** | **−100** | 双保险，前面已硬过滤 |

**为什么"用户嘴上说的"给 +4，比节气还高？**

这是踩过的坑。早期这条完全没接，结果是「来点甜的」「我要减肥」
和「我好烦」选出来的菜单**一模一样** —— 因为前三条只反映"系统觉得你该吃什么"，
完全没听"你自己说要吃什么"。用户说了却被无视，是最伤体验的一种。

**为什么人数匹配要单独给分、甚至给到 +5？**

因为菜单里真正的双人餐（¥54.9–73.9）名字里既没有节气关键词、也没有"辣/甜"，
按分数永远排不过「麦辣鸡腿汉堡套餐」，于是 2 个人只能拿到"单人餐 ×2"。
必须让"够吃"这件事本身成为理由。

### 7. 打分之后还有四道闸

分数只决定谁排前面，能不能进菜单还要过结构约束 —— 这部分才是"像不像人点的"的关键：

```
① 忌口硬过滤     同义词扩展（辣→香辣/麻辣/辣酱…），命中直接踢出候选池
                 ⚠️ 不是降权，是排除。过敏不能赌。
                    ↓
② 第一轮：整餐优先  按"人数匹配档位"分层，不按分数排
                 0 档 serves == people  （一份刚好够所有人）
                 1 档 serves >  people  （一份有余）
                 2 档 serves >= 2       （多人餐，份数叠上去）
                 3 档 serves == 1       （单人餐，凑不出才用）
                 ⚠️ 做成结构优先级而不是加权重，因为这两类商品
                    在总价/剩菜/饮品份数上根本不可比。
                    ↓
③ 第二轮：补缺口   整餐没喂饱 → 用单品汉堡补
                    ↓
④ 第三轮：配配角   小食/饮料/甜品，受结构上限控制
                 甜品 ≤1 个 SKU、饮品 ≤人数、小食 ≤人数(+1 余量，仅 1–2 人)
                 ⚠️ 配角单价不得超过主餐的 60%
                    （否则 ¥55.9 双人餐后面会跟一份 ¥39.9 炸鸡拼盘）
```

这里有两个反复调过的地方，都留了注释：

- **份数必须 `ceil` 不能 `floor`**。试过 `floor`（想省掉 3 人时的多余 1 人份），
  结果 3 人拿到「双人餐 ×1」后还差一个人，又补一份单人餐，而单人餐份数是 `min(people,4)=3`
  —— 最终 5 人份、价格翻倍。**多 1 人份远好过点错一顿**。
- **套餐自带的饮料要记进结构额度**。早期没记账，一份含可乐的套餐后面
  又补了一杯无糖可乐 —— 一个人一餐两杯饮料。

### 8. LLM 到底在哪一步

这是最容易被误解的一点。整条链路上 LLM 只出现在**四个**位置，而且一个都不许选品：

| 位置 | LLM 做什么 | LLM **不能**做什么 |
|---|---|---|
| 意图解析 | 判 `clear` / `vague`，抽人数/预算/忌口/口味/情绪 | 不给建议、不报价格 |
| 模糊旁路 | 结合记忆 + 时间，产出倾向标签 | 不选商品 |
| 出单复核 | 看这一单 + 购物车，判 `keep`/`minor`/`major` | 动作走白名单，本地执行 |
| 表达 | 写 `hook` + `quote` 两段文案 | 不写菜单、不写价格 |

`clarity` 由模型判定这一点很关键。旧版是规则推的，于是「帮我点个午餐」因为
没有人数/预算/口味被判成模糊，被反问「想吃带劲的还是舒服的」——
用户已经说要吃饭了，还问他想吃哪种感觉。

**规则层为什么不能退休**：忌口是硬约束，漏一个就是吃出问题，不能赌模型每次都抽到。
所以合并原则是 `taboo` 取**并集**（模型漏了规则补），`clarity/mood` 则是**模型说了算**。

**复核环节也只做减法或重配**：`minor` 时本地删掉多出来的那杯饮料（只删不加，价格必然只降不升）；
`major`（骨架不对，比如一个人三个主食）时把"最该换掉的名字"带回选品，
让**规则**在同一批真实商品里重新组一单。模型从头到尾没有选品权。

### 9. 于是同一个人、同一句话，不同时间会得到不同的菜单

把五个维度叠起来，能看出它为什么"看起来在动"：

**同一个烦躁的人，换一天：**

```
霜降（10/23–11/6）                    立冬（11/7–11/21）
keywords: 热可可/板烧/浓汤/汉堡/新地   keywords: 汉堡/热可可/浓汤/大份
strategy: 温热/高碳水/高满足感          strategy: 高热量/温热/进补
blurb: 贴秋膘这事该办了                blurb: 今天起所有的热量都算进补
        ↓                                    ↓
"板烧" 在表里 → +3                    "板烧" 不在表里 → 这 3 分没了
"新地" 在表里 → +3                    "新地" 不在表里 → 这 3 分没了
"大份" 不在表里                        "大份" 在表里 → 大份商品 +3
        ↓                                    ↓
同一批商品、同一个心情，只因过了一个节气，排序就变了
```

（霜降的关键词是 5 个、立冬也是 5 个，但只有 `汉堡/热可可/浓汤` 三个重合 ——
换季时真正被换掉的是 `板烧/新地` 和 `大份` 这两个方向的权重。）

值得注意的是：**"辣"从来不是任何一个节气的关键词**（24 个节气全部核对过）。
所以「烦躁 → 吃辣」这条路永远拿不到节气那 3 分 —— 它靠的是情绪策略的 +2。
节气管的是"热的、扎实的、大份的"，情绪管的是"甜、辣、冰"，两套词表是**正交**的，
叠加起来才是"霜降天吃甜辣的、热乎的"。

把 24 个节气的关键词全部去重，实际只有这 20 个词：

```
热饮 · 热可可 · 热咖啡 · 浓汤 · 汉堡 · 板烧 · 鸡肉 · 麦麦鸡 · 薯条 · 沙拉
新地 · 甜品 · 冰淇淋 · 冰品 · 冰饮 · 可乐 · 柠檬 · 大份 · 套餐 · 新品
```

看这份词表能反推出设计取向：**它几乎全是"温热的、热量高的、甜的和冰的"**，
唯独没有辣。这不是漏了，是因为冬天的季节性在麦当劳菜单上就体现在"热饮 + 甜 + 大份"上，
而"辣"是全年都在的常驻口味，用季节去筛它没有意义 —— 它归情绪管。

**同一个人，换一种情绪：**

```
烦躁 → tasteStrategy 甜/辣/冰    +2 命中新地、热可可、麦辣鸡翅
       avoid 清淡/轻食沙拉/小份   −5 压掉沙拉
       warmth 俏皮                → 甜 + 辣 + 热，「烦就对了，这天的锅不该你背」

低落 → tasteStrategy 温热/甜/软糯 +2 命中热可可、新地
       avoid 刺激/玩梗/星座话术    −5 压掉辣；话术层同时关掉星座与节气
       warmth 温和                → 温和、不玩梗，「今天不用勉强自己开心」
```

两单可能都含新地和热可可，但**理由和语气完全不同**：一个在陪你骂，
一个只是安静地把热的递过来。同一份数据、同一套规则，语气温度那一个字段把它分开了。

**再加一层记忆（老用户回归）：**

命中的是 `+3 本命单品`、`+2 特制习惯`、`+1 平时价位`，这三条让菜单从"合理"变成"你的"。
「4 个人 150 块」那单最后是 ¥122，靠的也是记忆里的价位区间而不是瞎猜。

实际输出（这是真跑出来的，不是示意）：

```

可用的节气文案：霜降是秋天最后一个节气，贴秋膘这事该办了。
【星座】天蝎座，爱恨分明，要么清汤要么爆辣。取向：重口、辣、极致。
```

把同一份策略交给选品，看每件商品实际得了多少分、为什么：

```bash
cat > probe2.ts <<'EOF'
import { composeStrategy } from './src/services/knowledge.service.js';
import { selectProducts } from './src/services/selector.service.js';
import { parseIntent } from './src/services/intent.service.js';

const now = new Date('2026-10-25T19:30:00');
const ctx = composeStrategy({ now, mood: '烦躁' });
const intent = parseIntent('我好烦啊', now);

const products = [
  { name: '热可可', price: 13, category: '饮料' },
  { name: '新地（巧克力）', price: 11.5, category: '甜品' },
  { name: '麦辣鸡翅', price: 8, category: '小食' },
  { name: '蔬菜沙拉', price: 12, category: '小食' },
  { name: '鲜煮玉米杯', price: 9, category: '小食' },
];

const r = selectProducts({ products, strategy: ctx.solarTerm,
  moodStrategy: ctx.moodStrategy, snapshot: null, intent, people: 1 });

for (const d of r.details) {
  console.log(String(d.score).padStart(3) + '  ' + d.product.name + '  | ' + d.reasons.join('，'));
}
EOF

npx tsx probe2.ts
```

```
  5  新地（巧克力）  | 应季（新地），对情绪有用（甜）
  5  热可可  | 应季（热可可），对情绪有用（甜）
  2  麦辣鸡翅  | 对情绪有用（辣）
  0  鲜煮玉米杯  | 顺手加一份
 -5  蔬菜沙拉  | 此时不合适（清淡）
```

这五行正好把机制说完了：

- **新地 / 热可可 拿 5 分**：`新地`和`热可可`都在霜降的 `keywords` 里（+3），
  同时「甜」命中烦躁的 `tasteStrategy`（+2）。**两个维度叠加**，这是它们排前面的真实原因。
- **麦辣鸡翅只有 2 分**：这里有个反直觉的地方 —— "辣"**不是**霜降的关键词，
  所以它拿不到 +3，只有「对情绪有用（辣）」的 2 分。
  换成立冬（keywords 里也没有辣）结果一样；但如果今天用户的情绪不是烦躁，
  它会掉到 0 分。**同一个"辣"，值多少分取决于今天是哪天、你是什么心情。**
- **蔬菜沙拉 −5**：不是因为沙拉不好，是烦躁的 `avoid` 里有「轻食沙拉」。
- **鲜煮玉米杯 0 分**：它既没命中节气关键词，也没命中 avoid，不奖不罚。
  （它并不在"清淡"的 avoid 里 —— `avoid` 只匹配字面「清淡/轻食沙拉/小份」，
  玉米杯这类边缘商品是靠 `+0` 自然排到后面，而不是被扣分。）

### 11. 这套做法的代价

不写收益，写代价，因为代价才是真的：

- **静态表会过期**。水逆区间只写到 2027，节气日期按非闰年近似。过期后不会崩，就是"应季"会变味。
- **关键词匹配是糙的**。商品改名、上新品，`keywords` 不跟着改就命中不到。这是查表法的固有限制，
  不是 bug。
- **多一层规则就多一层调参**。`ceil` vs `floor`、60% 配角上限、小食余量只给 1–2 人 ——
  全是拿真实菜单一遍遍调出来的，没有理论最优解。
- **"懂你"被拆成了查表和打分**。这套东西能保证不翻车、可复现、可单测，
  但它确实不是"理解"，是"匹配得足够细"。

之所以还是选这条路：**演示不能翻车**。一个靠 LLM 临场发挥的菜单，
好看的时候很好看，翻车的时候用户连"为什么推荐这个"都问不出来。

---

### 三条关键设计决策

**1. 单体不拆微服务**

演示规模下单进程绰绰有余，拆开只会让部署变复杂、让 SSE 跨进程传递变得麻烦。
`instances: 1` 是刻意的，不是偷懒。

**2. 规则做"想"，LLM 只做"说"**

这是最硬的一条边界：

- 情绪识别 → 规则引擎（关键词 + 优先级 + 反讽检测）
- 节气/星座映射 → 静态查表
- 选品 → 确定性打分（同输入必然同输出，可单元测试）
- **只有 hook/quote 的措辞交给 LLM**

代价是文案不如纯 LLM 灵活，收益是**演示绝不翻车**：断网、LLM 挂了、MCP 挂了，
菜单都还是对的。LLM 只是让它说得更好听。

**3. Token 服务端持有，用户不感知**

用户粘贴一次 Token，之后所有 MCP 调用都由服务端代持 —— 前端永远看不到 Token，
浏览器只拿一个 httpOnly Cookie。这让"AI 用你自己的会员账号下单"成为可能，
同时把 Token 泄露面压到最小。

## 安全与隐私

| 项 | 做法 |
|---|---|
| **Token 存储** | AES-256-GCM 加密后落库，格式 `base64(iv12‖tag16‖ciphertext)`。明文只在内存中存在 |
| **Token 日志** | 所有日志出口过 `sanitize()`，Token 显示为 `abcd****wxyz` |
| **Token 传输** | httpOnly Cookie `mcd_sid`（SameSite=Lax），前端 JS 读不到 |
| **记忆可删** | 记忆管理页逐条删除，或输「删除」二字一次性解绑清空全部数据 |
| **不代付** | `create-order` 只返回 `payUrl` 并透传展示。**代码库中没有任何支付/退款路径** |
| **金额不可篡改** | 服务端用 `calculate-price` 重算，**永不相信前端传来的金额** |
| **越权防护** | 所有订单操作校验 `orders.user_id === req.userId`；confirm 时还校验 `menuHash` 快照 |
| **SQL 注入** | 全参数化查询 |
| **密钥管理** | 缺失或格式错误直接拒绝启动；`.env` 在 `.gitignore` 里；`chmod 600` |
| **限流** | 每用户 20 req/min、全局 550 req/min（平台 600，留 50 边际） |

安全审计的完整记录（8 项扫描的真实输出）在 [docs/security-audit.md](docs/security-audit.md)。

## 常见问题

**Q：Token 从哪来？**

[open.mcd.cn](https://open.mcd.cn) → 扫码登录 → 控制台激活 → 复制 Token。免费。

**Q：Token 失效了怎么办？**

重新去 open.mcd.cn 生成一个，在登录页粘贴即可。
注意：**换 Token = 新身份 = 新记忆库**（userId 由 token 派生，这是设计取舍）。
旧记忆仍在服务端，用旧 Token 还能登回去看。

**Q：提示 429 了？**

两层限流：本服务（每用户 20 次/分钟）和麦当劳平台（600 次/分钟）。
等一分钟再试。如果是访客模式，可能是当日免费次数用完了 —— 登录后不限。

**Q：能不能不登录直接用？**

可以，访客模式每天 1 次免费对话。但访客没有记忆，
这个产品最值钱的部分（"它记得你"）就体验不到了。

**Q：数据存在哪？**

你自己服务器上的 `server/data/mcd.db`（SQLite）。没有第三方，没有云数据库。
备份用 `scripts/backup.sh`。

**Q：MCP 挂了还能用吗？**

能。会走离线兜底菜单，并在界面上明确标注「参考菜单，实时价格待确认」。
不会假装拿到了实时数据。

**Q：LLM 挂了还能用吗？**

能。回复走 `prompts/fallbacks.ts` 里的模板，菜单和价格完全不受影响（因为菜单从来不是 LLM 生成的）。

**Q：为什么不能自动付款？**

这是麦当劳平台的责任设计，也是本产品的安全底线。
`create-order` 只返回支付链接，**付款必须由你本人完成**。
Agent 无法、也不应该代付。


测试覆盖的重点：

- **节气/星座边界**：365 天全覆盖，10/22=寒露、10/23=霜降、11/6=霜降、11/7=立冬
- **选品确定性**：同输入 100 次结果完全一致
- **忌口硬过滤**：含忌口商品永不出现在菜单里
- **记忆去重**：topItems≤5、同日同情绪覆盖、200 字符截断
- **SSE 跨 chunk**：逐字节切分（中文多字节被切断）不崩、不乱码、不丢事件
- **金额语义**：`price` 是小计不是单价（这条契约写死）
