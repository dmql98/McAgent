## 一、项目背景

「麦门知己」是麦当劳点餐 Agent。用户随便说一句话：

- 情绪化："我好烦啊"
- 明确指令："明天中午4个人，预算150，有人不吃辣"

### 3.1 `services/intent.service.ts` —— 多维意图解析

输入一句话，输出结构化意图：

```ts
export interface ParsedIntent {
  explicit: {
    people?: number;
    budget?: number;
    taboo: string[];        // 忌口/过敏，如 ["香菜","辣"]
    taste: string[];        // 口味偏好，如 ["甜","辣"]
    fulfillment?: "自取" | "外送" | "堂食";
    timeHint?: string;      // 原始时间表述，如"明天中午"
    targetDate?: string;    // 解析成 ISO 日期
  };
  mood: Mood | null;        // 6 类之一
  moodConfidence: number;   // 0-1
  needsClarify: boolean;    // 是否该反问
  clarifyQuestion?: string; // 反问话术
  raw: string;
}
```

**第一级：规则引擎（默认路径，必须可靠）**

(a) 显式约束抽取（正则 + 关键词）
- 人数：`(\d+)\s*[个位人]`、"我和同事"（→2）、"我们仨"（→3）、"一个人"/"自己"（→1）
- 预算：`(\d+)\s*(块|元|块钱)`、"预算XX"、"XX以内"、"不超过XX"
- 忌口：`不吃X`、`不要X`、`忌口X`、`过敏X`、`X过敏`、`免X`、`少X`、`去X`
  —— 注意"不吃辣"要抽出 `辣` 并标记为 taboo，同时"不辣"≠"不吃辣"（前者是口味，后者是硬约束）
- 口味：`想吃X`、`要X`、`多X`、`加X`、`甜/辣/咸/冰/热`
- 取餐方式：`自取`/`到店`/`外送`/`送来`/`堂食`
- 时间：`今天/明天/后天/今早/明午/晚上/下午/现在` + `\d+点` → 解析成 `targetDate`（ISO）

(b) 情绪分类（关键词表 + 优先级）
6 类：烦躁 / 疲惫 / 低落 / 开心 / 平淡 / 庆祝
- 烦躁：烦、气死、崩溃、无语、受不了、抓狂、火大、裂开、绷不住
- 疲惫：累、困、熬夜、加班、没力气、瘫、虚、扛不住、肝
- 低落：难过、emo、想哭、失落、孤独、委屈、丧、抑郁、心累
- 开心：开心、爽、棒、美滋滋、太好了、赞、舒服
- 庆祝：庆祝、生日、升职、拿到、中奖、约、聚、过节、纪念
- 平淡：无明确情绪词 → `平淡`（confidence 低）

**优先级规则（重要）**：负面情绪优先于正面。
"累死了但终于搞定了" → 疲惫（不是开心），因为用户真实状态是累。
实现：按 烦躁 > 低落 > 疲惫 > 庆祝 > 开心 > 平淡 的顺序匹配，第一个命中即返回，
但 confidence 按命中词数量加权。

(c) 讽刺/反语检测（这条能显著提升"懂你"感）
"太好了呢"、"真棒啊"（带"呢/啊"且前面没感叹号）→ 降级为 烦躁，confidence 0.5。
实现简单规则即可，别搞复杂 NLP。

(d) 置信度与反问
- 有明确情绪词 + 有显式约束 → confidence 0.9，`needsClarify=false`
- 只有情绪词 → confidence 0.7，不反问（直接给情绪菜单，这是核心场景）
- **只有模糊表述**（"随便"、"不知道吃什么"、"都行"、"看你的"）→ confidence 0.3，
  `needsClarify=true`，问一个**有信息量的二选一**：
  "听起来你今天想吃点带劲的还是想吃点舒服的？" / "是要给自己加个油，还是想被安慰一下？"
  —— **反问本身是情绪价值，不能问成表单**（不要问"请输入人数和预算"）
- 极端低落（命中"想死"、"活着没意思"、"不想活"等）→ `mood = 低落`，`warmth = 温和`，
  **禁止玩梗**，回复里附一句真诚关怀（见 §3.4 安全模式）

**第二级：LLM 兜底（JSON mode）**
仅当 `confidence < 0.4` 且规则完全没抽到显式约束时，调 LLM：
```json
{"mood":"烦躁","explicit":{"people":null,"budget":null,"taboo":[]},"reasoning":"..."}
```
LLM 失败两次 → 直接走 `needsClarify=true`。**不要让 LLM 兜底成为主路径**。

### 3.3 `services/orchestrator.ts` —— 五层流水线（核心）

用 `AsyncGenerator` 推事件，供 `/api/chat` 转 SSE：

```ts
export type OrchestratorEvent =
  | { type: 'stage'; stage: 'intent'|'knowledge'|'menu'|'coupon'|'compose'; text: string }
  | { type: 'delta'; text: string }
  | { type: 'reply'; payload: ChatReply }
  | { type: 'done'; chatId: string }
  | { type: 'error'; error: string; message: string };

export async function* runChat(input: {
  userId: string | null;   // null = 访客
  message: string;
  guest?: boolean;
}): AsyncGenerator<OrchestratorEvent>
```

**流水线步骤（严格按架构 §7.2 时序）**：

**⓪ 身份与记忆**
- 有 userId → `memoryService.snapshot(userId)`
- 访客 → 空快照（不落盘）
- 这里**不推 stage**（太快了，用户看不到）

**① 意图解析** → 推 `stage: intent, text: "让我想想你想吃什么…"`
- `intentService.parse(message)`
- `needsClarify` 为真 → 直接跳到最后，推一个只有 hook 的 reply（反问），不进菜单

**② 知识匹配** → 推 `stage: knowledge, text: "翻了翻节气和你星座的运势…"`
- `composeStrategy({ now, birthday: snapshot.profile.birthday, mood, taboo })`
- `strategyToPrompt(ctx)` 得到 L3 层文本

**③ MCP 现实校准** → 推 `stage: menu, text: "正在替你看菜单…"`
- 调 `query-nearby-stores`（或 `delivery-query-stores`，按 fulfillment）
  → 拿门店（优先用户记忆里的 `usualStore`，没有就取最近的）
- 调 `query-meals`（带 storeId + 时段）→ 真实可售菜单
- 按策略**在真实菜单里选品**（见下方"选品算法"）
- 对选中的 1-2 个主推品调 `query-meal-detail` 拿特制项（去冰/加辣/去酱）→ 推
  `stage: coupon, text: "顺便翻了翻你的优惠券…"`
- 调 `available-coupons` + `calculate-price` → 券后价、原价、预算校验
- `list-nutrition-foods` 拿热量（失败就不写热量，不阻塞）
- **任一步失败**：
  - `AuthError` → 推 `error: TOKEN_INVALID`，结束（前端弹重新登录）
  - `RateLimitError` → 用缓存菜单继续，hook 里加一句"网络有点挤，先给你看这版"
  - `McpDownError` → 走**离线兜底**：用 `web/mock.js` 同款静态菜单（标明"参考菜单，实时价格待确认"），
    保证 demo 不断

**选品算法（确定性，不用 LLM 选）**
```
候选 = query-meals 返回的全部商品
过滤：① 时段可售 ② 命中 taboo 的直接排除（名称/配料含忌口词）③ 用户过敏项绝对排除
打分：
  +3 命中 strategy.keywords（节气推荐品类）
  +3 在 user.taste.topItems 里（本命单品）
  +2 口味匹配 moodStrategy.tasteStrategy（甜/辣/冰/热）
  +2 命中用户 taste.customs（如"可乐去冰"）
  +1 价格在 habits.budgetRange 内
  -5 命中 moodStrategy.avoid
排序取 top N（N 由人数决定：1人3-4件、2人4-5件、3-4人5-7件）
预算约束存在时：贪心装入直到超出预算，超了就降级替换更便宜的同品类
```
**关键**：选品是纯规则，可复现、可调试。LLM 不参与选品，只负责解释"为什么选这些"。

**④ 输出生成** → 推 `stage: compose, text: "给你写点人话…"`
- 组装五层 system prompt（见 §3.4）
- 调 LLM 生成 `{ hook, quote }` 两段文本（**只生成文字，不生成菜单结构**）
- 菜单结构由 `reply.renderer` 用选品结果直接产出（价格永远来自 MCP，杜绝编造）
- LLM 失败 → 用 `prompts/fallbacks.ts` 的模板拼 hook/quote（每个情绪+节气组合一条，
  至少覆盖演示的三个场景）

**⑤ 交易与落盘**
- 推 `reply` 事件（完整 JSON）
- 存 chat 记录到 `chats` 表（含菜单快照 hash，供 M6 下单校验）
- 记忆落盘：`addMoodEntry`（情绪日记）、`appendFact`（本轮抽到的新偏好，如"不要香菜"）
- 推 `done: { chatId }`
- **注意**：记忆落盘要在 `done` 之前完成，且失败不能影响用户（catch 后只打日志）

### 3.4 `prompts/` —— 提示词工程（决定效果上限）

`prompts/system.ts` —— 五层装配，严格按架构 §9.2：
```
[L1 人设]   "麦门知己"：不是客服，是懂你的老友。
            语气：像朋友，不像服务员。会说"我"，会说"你"。
            玩梗边界：能玩节气/星座梗，但绝不用在用户真难过的时候。
            禁止：亲爱的用户、您好、以下是为您推荐、希望能帮到您。
            长度：开场 2-3 句，收尾 1-2 句。宁短勿长。

[L2 记忆]   用户记忆快照（M2 的 snapshot）+ 明确指令：
            "引用要具体 —— 说'上周四你烦躁时吃了麦麦鸡'，
             不要说'根据您的历史记录'。没记住的就别提，禁止编造记忆。"

[L3 知识]   strategyToPrompt 的输出（节气 + 星座 + 时段 + 情绪策略）
            + 指令："必须点明出处，让用户知道你为什么这么推荐。"

[L4 事实]   真实菜单数据（JSON）+ 硬约束：
            "只能从这里选品和报价。禁止编造任何商品名、价格、优惠。
             菜单结构已由系统生成，你不需要输出菜单。"

[L5 输出]   严格 JSON：{"hook": "...", "quote": "..."}
            禁止输出 markdown、禁止输出菜单列表、禁止多余字段。
```

`prompts/fallbacks.ts` —— 模板兜底（LLM 挂掉时用）：
为以下组合各写一条 hook + quote（至少 12 条）：

- 低落（温和模式）× 任意
- 疲惫 / 开心 / 平淡 / 庆祝 × 通用

`prompts/stage-texts.ts` —— SSE 阶段文案，每个 stage 至少 3 条随机选，
避免每次都一样（"正在替你看菜单…"/"翻了翻今天的可售…"/"看看哪几样还热着…"）。

`prompts/safety.ts` —— 安全模式：
- 极端低落关键词表 → 触发 `warmth: 温和`

- 并追加一句真诚的关怀（不硬塞心理热线，除非明确自伤表述）

### 3.5 `services/reply.renderer.ts`
把选品结果 + LLM 文本拼成 `docs/contract.md` 定义的 `ChatReply` JSON。
- `price` = 该项小计（契约已定）
- `original` / `total` 来自 `calculate-price`，缺失时用菜单价累加并标注
- 预算约束存在时填 `budget: {limit, ok, remaining}`
- `actions`：正常 `["confirm","refine"]`；反问场景 `[]`；访客附 `upsell:"login"`
- **所有数字必须来自 MCP 或明确的 mock 兜底，不允许 LLM 给**

### 3.6 `routes/chat.ts`
`POST /api/chat`：接 `runChat`，把事件流转成 SSE（`text/event-stream`）。
- 每个事件 `event: <type>\ndata: <json>\n\n`
- 头部：`Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`
- 客户端断开 → `AbortController` 中止流水线，别继续烧 MCP 额度
- 访客限流：每 IP 每日 1 次（从 `db` 或内存计数，简单实现）
- 错误处理：`AuthError` → SSE 推 error 事件后关闭；其他异常 → 同上但 log 完整堆栈
