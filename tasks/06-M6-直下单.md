## 一、项目背景与关键边界（先看这条，最重要）

所以本任务要做的是：**建单自动化 + 支付交给人**。任何试图"自动付款"的实现都是错的。

## 三、本任务范围

### 3.1 后端：`services/order.service.ts`

**`confirmOrder(userId, chatId, opts)`** 流程：

1. **归属校验**（越权防护，必须做）
   - 查 `chats` 表：该 `chatId` 是否属于 `userId`？不是 → `403 UNAUTHORIZED`
2. **快照一致性校验**（防篡改，架构 §10 明确要求）
   - 从 chat 记录里取出菜单快照 + 当时的 `menuHash`
   - 重新计算当前订单项的 hash，**与快照 hash 不一致 → `409 ORDER_CONFLICT`**
     （含义：菜单在你确认期间变了，请重新确认）
   - 这里要防的是：前端传上来的菜单被改过（用户不该能改价格）
3. **价格复核**
   - 调 `calculate-price` 用**当前真实价格**再算一遍
   - 与快照总价差异 > 0.01 → `409 ORDER_CONFLICT`，返回新价格让前端提示用户
4. **建单**
   - 调 `create-order`，入参按 `docs/mcp-tools.md` 的实测结果
   - 返回 `{ orderId, payUrl }`
   - 建单成功后立刻写入 `orders` 表：`status='created'`、`menu_json`、`total`、`pay_url`
5. **记忆更新**
   - 调 `memoryService.recordOrder(userId, {...})` 更新 habits（常点单品排序、预算区间）
   - **注意**：这里更新的是"点了什么"，不代表"付了钱"；`status` 后续变更时再补
6. 返回 `{ orderId, payUrl, total, store, expiresAt? }`

**幂等性（重要）**：
- 同一个 `chatId` 重复 confirm → **返回已有订单，不重复建单**（防止用户连点两次产生两笔订单）
- 实现：`orders` 表按 `chat_id` 查，存在且 status 未 canceled → 直接返回
- 若已有订单是 `canceled` → 允许建新单（并记一条日志）

**`getOrderStatus(userId, orderId)`**：
- 归属校验 → 调 `query-order` → 映射状态
- 返回 `{ status, progressText, payUrl?, updatedAt }`
- 状态映射（按 MCP 实际返回值调整，若不确定先按这套，联调时修正）：
  - `created` → "订单已创建，等你付款"
  - `paid` → "收到钱了，正在准备"
  - `progress` → "正在为你出餐…"
  - `done` → "可以取餐了"
  - `canceled` → "订单已取消"
- 状态变化时**同步更新 `orders` 表**，`done` 时再更新一次 habits（真实完成）

**`cancelOrder(userId, orderId)`**：
- 归属校验 → `cancel-order` → 更新表状态
- 只允许 `created` / `paid` 状态取消（`progress` 之后调 MCP 会报错，原样透传错误）

### 3.2 后端：`routes/orders.ts`

- `POST /api/orders/confirm`，body `{ chatId }` → `confirmOrder`
- `GET /api/orders/:id` → `getOrderStatus`
- `DELETE /api/orders/:id`（或 POST `/cancel`）→ `cancelOrder`
- 全部走 `middleware/jwt.ts`（必须登录，访客不能下单）
- 错误映射按 `docs/contract.md` 的统一错误体

**"免确认一键下单"开关**（PRD §7 提到）：
- 用户设置项，**默认关闭**
- 开启后前端可以跳过"复述菜单"这一步直接 confirm
- 但**服务端的归属校验和快照校验永不跳过**（开关只影响前端多一次点击）
- 本任务只需在 `users` 表加一个 `auto_confirm INTEGER DEFAULT 0` 列（若 M1 建的 schema 没有，
  用 `ALTER TABLE` 加，写在 `db/migrations/` 下），并在 `GET /api/me` 里带出

### 3.3 前端：`web/app.js` 的下单部分

**(a) 确认下单**
- 用户点 `actions` 里的"确认下单" → 先**复述一遍**（PRD §7 建单确认制）：
  在气泡下方插入一条确认条："「水逆急救单」¥39.5 · 留仙洞店 · 自取，确认建单？" + [确认] [再想想]
  - 若 `auto_confirm=true` → 跳过这一步
- 点[确认] → `POST /api/orders/confirm {chatId}`
- loading："正在建单…"（按钮禁用）

**(b) 支付卡片**（拿到 payUrl 后）
沿用 demo 的设计语言（红/黄/米底、圆角 14px）：
```
┌─────────────────────────────┐
│ 订单已创建 · 共 ¥39.5         │
│ 留仙洞店 · 自取               │
│ ┌─────────────────────────┐ │
│ │   点击去付款（扫码/链接）  │ │   ← 主按钮，红色
│ └─────────────────────────┘ │
│ 付款由你完成，我只负责下单     │   ← 小字，灰
└─────────────────────────────┘
```
- 点击按钮 `window.open(payUrl, '_blank')`（PRD 明确 payUrl 只透传展示）
- **不要内嵌二维码渲染**（我们不知道 payUrl 是不是扫码链接，别猜）
- 若 `payUrl` 为空 → 显示"订单已创建，但没拿到付款链接，去麦当劳 App 里查看"

**(c) 进度轮询**
- 支付卡片出现后开始轮询 `GET /api/orders/:id`，间隔 **3 秒**（前 30 秒）→ **10 秒**（30 秒后）
- **上限 5 分钟**，超时停止并显示"还没收到付款，稍后在订单页看"
- 页面切到后台（`document.hidden`）时暂停轮询，切回来恢复（省资源，也是礼貌）
- 状态文案变更时更新卡片（"正在为你出餐…" 用打字机或淡入，不要太跳）
- `done` → 卡片变成"可以取餐了 🍟" + 停止轮询 + **刷新一次记忆面板**（证明它记住了）
- `canceled` → "订单已取消" + [重新点一单] 按钮

**(d) 错误处理**
- `ORDER_CONFLICT` → "菜单价格刚刚变了（现在 ¥XX），要按新价格下单吗？" + [按新价下单] [算了]
- `TOKEN_INVALID` → 弹"麦当劳授权过期了，重新登录一下" + [去登录]
- `RATE_LIMITED` / `MCP_DOWN` → "麦当劳那边有点忙，稍后重试" + 保留按钮可重试
- 网络错误 → 同上

### 3.4 安全清单（逐条实现，这是本任务的重点）

| 项 | 要求 |
|---|---|
| 归属 | 任何订单操作必须校验 `orders.user_id === req.userId` |
| 快照 | confirm 时校验 chatId 归属 + menuHash 一致 |
| 价格 | 服务端重算，**永不信前端传来的金额** |
| 幂等 | 同 chatId 重复 confirm 返回同一订单 |
| 支付 | 无任何代付/自动支付代码路径；payUrl 仅透传 |
| 日志 | 订单号可打，**payUrl 不打全（打前 20 字符 + …）** |
| 访客 | 访客无下单权限，直接 401 |

## 四、硬性约束

1. **绝不实现任何自动支付**。没有 pay/refund 相关代码，一个字段都不要有。
2. **服务端不信前端**：金额、菜单、门店，全部服务端重算或从快照读。
3. **不改视觉定稿**。支付卡片沿用 demo 的设计语言（新组件，但同一套色/圆角/字重）。
4. 只改：`server/src/routes/orders.ts`、`server/src/services/order.service.ts`、
   `server/src/db/migrations/*`、`web/app.js`、`web/style.css`（追加支付卡片样式）。
   不改 `mcp/`、`orchestrator.ts`、`chat.ts`。
5. 轮询必须可中止（用户离开页面/关闭卡片要 clearInterval），**不要留野定时器**。
6. 所有 MCP 写操作**永不走缓存**（M3 已保证，但你要确认没绕过 gateway 直连）。
