## 一、项目基本信息

| 项 | 内容 |
|---|---|
| 项目名 | **麦门知己** |
| 一句话简介 | 一个能接住「我好烦啊」的麦当劳点餐 Agent |
| 赛道 | 用餐赛道（WaytoAGI 1024）／麦当劳 M-CODE |
| 形态 | Web 应用（移动端优先） |
| 技术栈 | Node.js 22 + Express 5 + TypeScript + SQLite + 麦当劳 MCP + OpenAI 兼容 LLM |
| 部署 | 单台服务器单进程，零外部 SaaS |

### 为什么是它

现有麦当劳点餐助手（包括平台自带的）都只能处理**结构化指令**：
"巨无霸套餐加可乐"。你说"我好烦啊"，它要么反问"您需要点什么"，要么给你推爆款。

但**人是带着情绪去吃饭的**。烦的时候想吃辣、累的时候想吃热乎的、
低落的时候不想被玩梗。这些信息点餐系统里没有，但对话里有。

「麦门知己」做的事：**把情绪、节气、星座、历史记忆都变成选品依据，
再用人话把理由说出来。**

## 二、核心创新点

### 创新 1：情绪输入接得住（不用给指令也能点餐）

用户说"我好烦啊"，不需要人数、预算、想吃什么。系统自己补全：

| 缺失信息 | 怎么补的 |
|---|---|
| 想吃几个 | 1 人 → 4 件（目标件数由人数推导，情绪场景默认 1 人） |
| 预算多少 | 读记忆里的 `habits.budgetRange`（¥25–45） |
| 吃什么口味 | 情绪策略：烦躁 → 甜 + 辣 + 冰 |
| 不要什么 | 读记忆里的忌口（香菜）+ 情绪 avoid（清淡/轻食/小份，因为烦的时候"健康说教"很讨嫌） |
| 现在几点 | 时段判断 → 夜市（17–22 点），决定推热饮还是冰饮 |

**这是"少输入多输出"**：用户给的信息越少，越需要系统有依据地补。

### 创新 2：跨会话记忆（用得越久越懂你）

记忆不是"存历史订单"这么简单。它分五层：

| 层 | 内容 | 怎么用 |
|---|---|---|
| 静态档案 | 昵称 · 生日 · 星座 · 忌口 | 忌口是**硬约束**（永不推荐），星座/生日用于开场 |
| 口味画像 | 甜度/辣度偏好 · 温

度 · 本命单品 Top5 · 特制习惯 | 打分加权（本命 +3、习惯 +2） |
| 习惯数据 | 历史订单 · 预算区间 · 常点时段 · 常去门店 | 默认值来源 |
| 情绪日记 | 每次对话的情绪 + 推荐 + 反馈 | 情绪回钩（"上周四你也是这么烦的"） |
| 仪式记忆 | 上次节气 · 水逆状态 · 生日提醒 | 避免重复提醒，制造"它记着"的惊喜 |

去重规则是契约的一部分（topItems≤5、同日同情绪只留一条、任意字符串≤200 字、整体≤8KB），
不是随便截断 —— 记忆要能长期用，不能无限膨胀。

**用户可完全控制**：记忆管理页逐条删除，或输「删除」二字一次性清空全部。

### 创新 3：节气 × 星座知识层（给推荐一个有文化的理由）

这是"情绪价值"的燃料。同样是推热可可：

- 没有知识层：「热可可 ¥13」
- 有知识层：「霜降限定情绪，热乎的才对」

实现是 24 节气 + 12 星座的静态表，加上水逆时段表。
每个节气带 `imagery`（意境）、`strategy`（策略标签）、`keywords`（选品关键词）、`blurb`（可直接用的文案）。

**关键设计**：知识层是**规则**，不是 LLM 生成。
LLM 可能把"霜降"说成"秋分"，但查表不会错。这类事实性内容必须确定。

## 三、技术亮点

### 亮点 1：MCP 深度使用（13 个工具，覆盖全链路）

不是只调一个 `query-meals`。13 个工具分布在 6 个阶段：

| 阶段 | 工具 | 用途 |
|---|---|---|
| 定位 | `now-time-info` | 登录时校验 Token + 判断可售时段 |
| 定位 | `query-nearby-stores` | 找门店，优先匹配记忆里的常去店 |
| 定位 | `delivery-query-stores` | 外送场景 |
| 选品 | `query-meals` | 门店+时段的可售菜单 |
| 选品 | `query-meal-detail` | 单品详情、套餐组成、**特制项可选值** |
| 叙事 | `list-nutrition-foods` | 热量（拿不到就不写，不瞎算） |
| 优惠 | `available-coupons` | 用户可用券 |
| 优惠 | `query-store-coupons` | 门店券 |
| 优惠 | `auto-bind-coupons` | 自动领券（**写操作，需口头确认**） |
| 交易 | `calculate-price` | 下单前价格复核（**服务端永不信前端金额**） |
| 交易 | `create-order` | 建单，返回 payUrl |
| 交易 | `query-order` | 进度轮询（3s→10s 退避） |
| 交易 | `cancel-order` | 取消 |

**工程处理**：

- **连接池**：每用户一条 MCP 连接，10 分钟空闲回收，最多 50 条 LRU
- **缓存分层**：只有只读白名单才缓存（菜单 10min、门店 5min、营养 24h）；
  价格/券/订单状态**永不缓存**（缓存会给出过期价格，风险高于收益）；写操作双重保险永不缓存
- **限流**：每用户 20 req/min、全局 550（平台 600，留 50 边际），先于麦当劳 429 拦下
- **错误三分法**：401→`TOKEN_INVALID` / 429→`RATE_LIMITED` / 5xx超时→`MCP_DOWN`，降级策略各不同
- **容错适配**：真实 schema 未知，所有响应走宽松适配器（`mcp-adapter.ts`），字段名多候选

### 亮点 2：规则 + LLM 分层（"规则做想，LLM 只做说"）

这是最硬的一条边界，也是整个系统可靠性的来源：

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 情绪识别 | **规则** | 关键词 + 优先级 + 反讽检测。可单测、可复现、零成本 |
| 节气/星座映射 | **规则** | 静态查表。事实性内容必须确定 |
| 选品打分 | **规则** | +3 节气命中 / +3 本命 / +2 情绪匹配 / +2 习惯 / +1 价位 / -5 avoid。**同输入必然同输出** |
| 忌口排除 | **规则** | 硬过滤 + 双保险，绝不交给概率 |
| 价格计算 | **MCP** | `calculate-price` 或快照重算 |
| hook/quote 措辞 | **LLM** | 只有这一步需要语言能力 |

**收益**：LLM 挂了、MCP 挂了、断网了，菜单还是对的。只是话说得朴素一点。

具体地说，`selectProducts()` 是纯函数，输入相同输出必然相同 ——
这条被写成了单元测试（同输入跑 100 次断言结果一致）。
演示前不需要"多试几次挑个好结果"，第一次就对。

### 亮点 3：单机自部署，零外部 SaaS

- **SQLite + `node:sqlite`**：Node 22 内置，不需要 `better-sqlite3` 的原生编译
  （省掉了 node-gyp / MSBuild 的一堆麻烦，`npm install` 在任何机器上都能过）
- **无 Redis**：缓存是进程内 TTL Map，连接池是进程内 Map
- **无消息队列**：SSE 直接挂在 HTTP 连接上
- **无对象存储**：没有文件上传需求
- **无 Docker**：`git pull && npm ci && npm run build && pm2 reload` 四条命令搞定

**代价**：不能水平扩容（`instances: 1` 是刻意的 —— SQLite 写锁 + 内存池会互相踩）。
**收益**：一台 2 核 2G 的机器就能跑，月成本 ~¥30，任何人都能自建。

| # | 工具 | 用在哪个环节 | 每次对话调用次数 | 缓存 |
|---|---|---|---|---|

| 5 | `query-meal-detail` | 特制项 | 0–2 | 10 min |
| 6 | `list-nutrition-foods` | 热量叙事 | 1（失败不阻塞） | 24 h |
| 7 | `available-coupons` | 查券 | 1 | 不缓存 |
| 8 | `query-store-coupons` | 门店券 | 0–1 | 5 min |
| 9 | `auto-bind-coupons` | 领券（写） | 0（需确认才调） | 永不 |
| 10 | `calculate-price` | 下单前价格复核 | 1（confirm 时） | 不缓存 |
| 11 | `create-order` | 建单（写） | 0–1 | 永不 |

**一次典型对话（场景①）的 MCP 调用量**：约 5 次（time-info 不算，因为登录时已调）。
远低于 600 req/min 的平台限额，但代码里仍然做了限流 —— 因为多人同时用会撞。

## 五、演示三场景脚本（可直接念）

### 场景① 情绪输入

> **念**：「这是最关键的场景。我只说了四个字：我好烦啊。
> 没有说人数、预算、想吃什么。」
>
> **操作**：输入「我好烦啊」→ 回车
>
> **念**：「注意它没有反问我『请问您需要点什么』。
> 它在读三样东西：第一，今天是霜降第二天；第二，水逆第 3 天；
> 第三 —— 我的生日是明天。
> 然后它给了我一单叫『水逆急救单』：新地、麦辣鸡翅、柠檬水、热可可。
> 每一样都有理由，比如热可可是『霜降限定情绪，热乎的才对』。
> 券后 39.5，原价 50。」
>
> **念**：「最后这句是我觉得最值钱的地方：『上周四你烦的时候吃了麦麦鸡说治愈』——
> 它在用我的历史情绪数据。」

### 场景② 明确指令

> **念**：「第二个场景是常规需求：明天中午 4 个人，预算 150，有人不吃辣。」
>
> **操作**：输入「明天中午4个人，预算150，有人不吃辣」
>
> **念**：「4 人餐、¥150 以内、1 份免辣。合计 145.5，剩余 4.5 ——
> 一分钱没超，因为预算是硬约束，装箱算法会跳过放不下的商品继续找便宜的。
> 那句『剩的 4.5 够加一个圆筒』是在预算内主动加价值，不是凑单。」

### 场景③ 老用户回归

> **念**：「最后这个场景，是我用了一段时间之后再回来。」
>
> **操作**：输入「我又来了」
>
> **念**：「我什么都没说。它说『哟，麦小门。三天不见，我可都记着呢』。
> 然后它记得三件事：上周四我烦躁、麦麦鸡治好了我；我的可乐永远去冰；明天我生日。
> 它给了一单『寿星专属』。
>
> **这就是跨会话记忆。** 用得越久它越懂你 ——
> 这话别的助手说不出，因为它们没记性。」

### 场景④ 下单（收尾）

> **操作**：点「确认下单」→ 出现确认条 → 点「确认」
>
> **念**：「下单前它会复述一遍：什么单、多少钱、哪家店、怎么取。
> 建单成功后出现支付卡片。」
>
> **操作**：点「点击去付款」
>
> **念**：「注意这里 —— **付款是由我本人完成的**。
> Agent 只负责建单，不碰钱。这既是麦当劳平台的设计，也是我们守的底线。」
>
> **念**：「状态会自动更新：等你付款 → 正在准备 → 正在出餐 → 可以取餐。
> 页面切到后台会暂停轮询，切回来恢复。」

## 七、可验证性声明

评委可以自己验证的部分：

1. **单元测试**：`cd server && npm test` → 91 个测试全绿
2. **类型检查**：`npx tsc --noEmit` → 零错误
3. **前端 E2E**：73 项断言覆盖完整交互链路
4. **无 Token 也能看界面**：`cd web && python -m http.server 8080` → mock 模式完整演示三场景
5. **安全审计**：`docs/security-audit.md` 含 8 项扫描的真实输出
6. **契约可查**：`docs/contract.md` 是所有接口的唯一事实来源，含错误码表、SSE 事件格式、ChatReply Schema

**代码里刻意"没有"的东西**（同样是设计声明）：

- 没有任何自动支付/代付代码路径
- 没有任何 `alert()`（提示都是内联 DOM）
- 没有前端框架、没有构建工具（浏览器直接跑 ES module）
- 没有一条 `if (USE_MOCK)` 散落在业务代码里（只有 `api.js` 一处开关）
