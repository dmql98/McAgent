04后端模块设计

auth.service

登录：前端 POST token → 调 MCP now-time-info 验证（401 拒绝）→ user_id = sha256(token).slice(0,16) → AES-256-GCM 加密 token 落库 → 签发 JWT(7d)。

memory.service

按 user_id 读写记忆 JSON（表内 TEXT 列）；提供 appendFact / updateTaste / addMood / snapshot()；每次写入后跑摘要去重（同 key 覆盖，mood_diary 追加）。

knowledge.service

纯函数模块：节气表（日期区间→意境+推荐策略）、星座库（星座+月份→策略）、情绪→口味策略、时段判定。零 IO，可单测。

intent.service

规则引擎：正则/关键词抽取显式约束（人数/预算/忌口/时段）与情绪分类；置信度不足时降级 LLM 结构化解析（JSON mode），再不足则反问一次。

orchestrator ★

AsyncGenerator：加载记忆 → 意图解析 → 知识匹配 → MCP 校准（逐事件推 SSE）→ LLM 生成回复 → 记忆落盘。每个阶段向 SSE 推 stage / delta / final 事件。

mcp/gateway ★

Map<user_id, Client> 连接池；调用时注入该用户解密后的 Bearer token；菜单类只读调用走 TTL 缓存；401 销毁连接并标记会话失效，429 走缓存降级。

llm.client

OpenAI 兼容封装：chat(messages, {json?})，超时 20s、重试 1 次；system prompt 分层装配（人设 + 用户记忆快照 + 知识上下文 + 本轮策略）。

reply.renderer

产出前端渲染 JSON：{hook, menu[], total, quote, actions}——前端按 demo 卡片样式渲染，不直接吃 markdown。

middleware

jwt 校验除 /auth 外全挂；内存限流：IP 30 req/min、chat 10 req/min（自部署防爬防滥用）。

05API 设计

方法路径说明请求 → 响应要点
POST/api/auth/loginToken 登录（唯一登录方式）{token} → 服务端 MCP 验证 → {ok, isNew, userId} + httpOnly JWT Cookie；401 → {error:"TOKEN_INVALID"}
POST/api/auth/logout退出（清 Cookie；不解绑）→ {ok}
DELETE/api/auth/unbind解绑：删加密 token 与全部记忆→ {ok}（前端二次确认）
GET/api/me当前用户 + 引导状态→ {userId, profile?, hasToken, needOnboarding}
PUT/api/profile三连问/资料修改{nickname?, birthday?, taboo?[]} → 自动推星座入库
POST/api/chat对话（SSE 流式）{message, guest?} → SSE：event: stage（解析/查知识/看菜单/领券）· event: reply（渲染 JSON）· event: done
POST/api/orders/confirm确认下单（直下单）{chatId, autoPay:false} → 服务端以用户账号 create-order → {orderId, payUrl, store}；建单后自动 query-order 轮询
GET/api/orders/:id订单进度→ {status, progressText}
GET/api/memory记忆管理页数据→ 分组卡片 JSON（profile/taste/habits/mood/rituals）
DELETE/api/memory/:key删除记忆条目→ {ok}
GET/api/health健康检查→ {ok, mcp:"reachable"}
访客模式实现：POST /api/chat 带 guest:true 时走同一 orchestrator，但记忆读写指向内存临时对象，且每个 IP 每日限 1 次完整对话；回复末尾附 upsell:"login" 标记，前端据此弹出登录引导卡片。

06数据模型（SQLite）

-- 用户与凭证（token 永不明文） CREATE TABLE users ( user_id TEXT PRIMARY KEY, -- sha256(token)[0:16] token_enc TEXT NOT NULL, -- AES-256-GCM(原始token) nickname TEXT, birthday TEXT, -- ISO 日期；星座由此推算 star_sign TEXT, taboo TEXT, -- JSON 数组：忌口/过敏 created_at INTEGER, updated_at INTEGER ); -- 用户记忆（五模块合一大 JSON + 独立情绪日记表） CREATE TABLE memories ( user_id TEXT PRIMARY KEY REFERENCES users(user_id), data TEXT NOT NULL, -- JSON: {taste, habits, rituals} version INTEGER DEFAULT 1, -- 乐观锁 updated_at INTEGER ); CREATE TABLE mood_diary ( -- 情绪日记（护城河，独立成表便于回溯） id INTEGER PRIMARY KEY AUTOINCREMENT, user_id TEXT, mood TEXT, -- 烦躁/疲惫/低落/开心/平淡/庆祝 trigger_text TEXT, -- 用户原话（脱敏截断 200 字） recommended TEXT, -- 推荐了什么(JSON) feedback TEXT, -- "治愈"等用户反馈 created_at INTEGER ); -- 订单留痕（对账与"记忆回钩"素材） CREATE TABLE orders ( id TEXT PRIMARY KEY, -- mcp 返回的 orderId user_id TEXT, chat_id TEXT, menu_json TEXT, total REAL, status TEXT, -- created/paid/progress/done/canceled pay_url TEXT, created_at INTEGER ); -- 对话留痕（可选，轮询清理 30 天前） CREATE TABLE chats ( id TEXT PRIMARY KEY, user_id TEXT, messages TEXT, created_at INTEGER -- JSON 数组 );
备份策略：sqlite3 data.db ".backup backup.db" 进 crontab 每日一次；整库即 data/ 目录一个文件，迁移服务器直接搬走。

08MCP 网关设计

关注点设计
连接池Map<user_id, {client, transport, lastUsed}>；空闲 10 分钟断开重连；上限 50 连接，LRU 淘汰
Token 注入StreamableHTTPClientTransport requestInit.headers 注入 Authorization: Bearer（解密后）；明文仅在内存存在
限流保护（600/min）① 菜单/门店/营养类只读调用统一走 TTL 缓存（菜单 10min、门店 5min、营养 24h，key=storeId+时段）；② 网关级令牌桶：每 user 20 req/min，先于麦当劳 429 拦下
错误映射401 → AuthError（销毁连接、会话标记失效、前端弹重新登录）；429 → RateLimitError（缓存降级回复"菜单先看旧的"）；5xx/超时 → McpDown（离线推荐兜底）
调用规范统一封装 callTool(userId, name, args, {cacheTtl})：写操作（create/cancel/bind）永不走缓存；TOON 紧凑格式响应统一在此解码
调试模式DEBUG_MCP=1 时打印工具名/参数/耗时（自动脱敏 token），方便开发期排查

09LLM 编排设计

9.1 两级解析，规则优先

第一级：规则引擎（默认）

意图解析与策略选择走静态规则：正则抽约束、关键词表分情绪、日期查节气、生日查星座。零 LLM 成本、结果确定、可单测，演示不翻车。

第二级：LLM 兜底（JSON mode）

规则置信度低（如"今天想吃点有故事感的"）→ LLM 结构化输出 {mood, constraints, strategy_hint}；两次失败 → 礼貌反问一次。

9.2 System Prompt 分层装配

[L1 人设] 麦门知己：懂你老友，语气温度规范、玩梗边界（极端低落→温和模式） [L2 记忆] 用户记忆快照（昵称/星座/忌口/口味/近 3 条情绪日记/水逆状态）——"引用要具体" [L3 知识] 本轮命中的节气 + 星座运势 + 时段 + 情绪策略（含推荐理由，要求回复点明出处） [L4 事实] MCP 返回的真实菜单/价格/优惠券/热量（硬约束：只能从这里选品与报价，禁止编造） [L5 输出] 固定 JSON Schema：{hook, menu:[{name,spec,why,price}], total, original, quote, actions}
为什么回复必须是结构化 JSON：前端按 demo 的菜单卡片/合计条/金句框组件化渲染，AI 不产 markdown——样式永远不翻车，价格永远来自真实数据。

9.3 话术库

  • quotes.md：30+ 条收尾金句按情绪分类，LLM 生成时随机注入 1 条做底稿再润色，保证"每次不一样但不尬"；
  • stage-texts：SSE 阶段文案（"正在替你看菜单…""翻了翻你的优惠券…"），前端打字机效果素材；
  • safety：极端低落关键词表命中 → 切换温和人设 + 禁玩梗 + 附一句真诚关怀。

10安全设计

层面措施
凭证Token AES-256-GCM（密钥=env TOKEN_ENC_KEY，独立于 JWT 密钥）；内存中明文最短化；日志/错误堆栈统一走脱敏器
会话JWT httpOnly + SameSite=Lax；7 天滑动续期；401 全局拦截
传输全站 HTTPS（Let's Encrypt）；HSTS 开启
注入防护用户输入只作为 data 进 prompt（system/role 固定），不做模板拼接；SQLite 全参数化；CSP 基线（前端无内联脚本执行第三方内容）
越权防护一切读写在 middleware 强制 req.userId 归属校验；订单 confirm 校验 chatId 属于当前用户且菜单快照 hash 一致
资金安全Agent 无任何支付能力（平台未提供，也不模拟）；payUrl 仅透传展示；一键下单开关默认关闭
滥用防护IP/用户双维内存限流；访客每日 1 次；健康检查不暴露版本信息

12部署方案（你的服务器）

① 基础：Node 22 + Nginx + certbot（HTTPS） ② 后端：git pull → npm ci → npm run build → pm2 start ecosystem.config.js ③ 前端：web/ 目录 → Nginx root；/api → proxy_pass http://127.0.0.1:3000 ④ 数据：首次启动自动执行 schema.sql 建库（data/mcd.db） ⑤ 证书：certbot --nginx 自动续期 ⑥ 备份：crontab 每日 sqlite3 .backup → data/backup/
Nginx 关键配置点：/api 反代时关闭缓冲（proxy_buffering off）以支持 SSE 流式；proxy_read_timeout 120s 兜住 LLM 慢响应。
