2模糊要不要反问不反问，走旁路替你想。只有"旁路也空手 + 上一轮没问过 + 非安全模式"才问一次，且禁止连问两次orchestrator.ts:284
3说，还是选选品、份数、报价全部是确定性代码；LLM 的输出被限制成 {hook, quote} 两个字符串，拿不到菜单写权限prompts/system.ts:72

8钱信谁不信 LLM、不信前端。到店重算、外送以 calculate-price 为准，差异 > 1 元就报冲突order.service.ts:246

注意 loop 的边界：它没有「工具循环」。LLM 不选工具、不决定调几次 MCP —— MCP 调用顺序是写死的 if/else。所谓 "agent" 体现在规则 + 知识 + 真实数据 + 一层模型判断合成一个回复，而不是模型自主编排。模型只在两个位置做"判断"：clarity（够不够清楚）和 review（这单配得像不像人点的）；两处都没有选品权。

① 参数校验

zod safeParse，失败直接 400，不开 SSE。

② 限流

/api 30 次/分（scope=api）；/api/chat 10 次/分。超限 429 + Retry-After。

③ 访客额度

SQLite guest_usage 计数，每 IP 每天 1 次；计数故障时放行，不挡用户。

03① intent：LLM 主导的意图解析

架构变更LLM 决策llm-intent.service.ts:221 parseIntentWithLlm() —— 模型出结构化意图，clarity 由模型判定；规则解析同步跑一遍，只做"约束抽取 + 安全网"。

为什么要把决策权从规则搬给模型：旧版靠"有没有 people/budget/taboo/taste"推清晰度，两头都判错 ——
① 「今天好烦」因为有"今天"这个时间词被判成清楚，直接硬选品，一句话被当成点餐指令；
② 「帮我点个午餐」因为什么约束都没有被判成模糊，反过来被问一句"想吃带劲的还是舒服的"。
根子是同一个：规则无法判断"光靠这句话能不能在菜单上挑出东西"。这句话判断标准只有一条，交给模型反而更准。

模型抽什么、规则补什么

字段谁说了算合并规则（mergeIntent）
clarity模型模型给 clear/vague 直接采信；给了非法值才退回规则。但有一条硬覆盖：只要忌口/预算/人数任一存在，强制 clear（:335）
mood模型模型值合法就采信，否则用规则的；命中后 moodConfidence = 0.85
orderIntent或运算模型或规则任一为 true 即 true
taboo并集 + 校验规则 + 模型取并集；模型新提的忌口必须在原文里找得到否定词搭配（不吃/过敏/忌口/别放…），否则丢弃。这条是防"模型把『想吃辣』写成不吃辣"，那会把整个辣味菜单全过滤掉
taste并集取并集后剔除已进硬忌口的，避免同一词既是偏好又是禁忌
people/budget模型优先模型给了取模型的（1–30 人 / 1–10000 元），没给用规则的（中文数字规则比模型稳）。模型被明确要求"没说就填 null，不要猜"
safetyMode或运算任一方命中即开，开则禁一切节气/星座/水逆话术
needsClarify恒 false新架构下模糊 ≠ 要反问，模糊走旁路。这个字段实际已退役（见 16 节 #8）

为什么规则不能退休

安全

忌口/过敏是硬约束，漏一个就是吃出问题，不能赌模型每次抽到。规则必须能捞回来。

可复现

中文数字（「仨」「两位」）、预算十几种说法，正则可单测、零成本、结果稳定。

降级

模型超时 9s / 挂了 / 返回乱码 → {...rule, clarity: ruleVagueToClarity(rule)}，用户照样能点餐

04①.5 购物车直改

必须在谁之前不这样的后果
反问分支这类句子通常很短、情绪很平，正好命中"太模糊"，于是用户说"删掉薯条"，系统回一句"你想吃带劲的还是舒服的"
选品走选品会把整份菜单换掉。用户只想删一份薯条，结果一单被重配
旁路（context）改车是确定性操作，让模型去分析"用户为什么想删薯条"纯属浪费一次调用，还会拖慢几百毫秒

识别顺序（不能调）

text 长度 > 40 → none（长句基本不是购物车指令，保守放行）

clear   ← 全部清空 / 都删了 / 清空购物车 / 全都不要 / 重新来一单 / 都不要了
swap    ← 把? (X) (换成|替换成|改成) (Y)
remove  ← 删 / 去掉 / 不要了 / 拿掉
setQty  ← 必须带明确动词：改成 / 改到 / 调成 / 变成 + 数字
add     ← 再加 / 再来 / 加个 / 来N杯 / 要N个 / 多要 / ^加
两处必须踩住的坑（都真踩过）：
① 「来两杯」必须归到 add，不能落到 setQty。早期漏了"动词+数量+单位"这条，用户说「可乐来两杯」被理解成"把某物改成 2 份"。
② setQty 必须有明确动词。「两个人吃 100 块」里的"两"会被当成数量，于是正常点餐请求被误判成"把某物改成 2 份"，整单一换全乱。

五个分支的实际行为

kind空车时非空车时找不到时的回复
clear直接清（无意义但不报错）clearCart()—
remove回"你还没点东西呢"findItemByName → removeItem车里没有「X」。现在有：…。要删哪个直接说名字
setQty同上updateItem({qty})车里没有「X」。现在有：…

add返回 null（当点餐处理）pickProduct → addItem({qty})菜单里没找到「X」，换个说法试试
三个细节值得单独说：
① 空车 + add/swap 要返回 null 而不是报错。「来杯可乐」在空车语境下更像"给我配一单"，不该只加一杯可乐就结束。
② swap 必须"先删后加"。顺序反了会短暂多出一件；而且若加购失败还能保住原来那份。
③ 「改不动」也要回 ChatReply 而不是走选品。用户说"把薯条删了"但车里没有薯条，如果走选品，他会收到一整份新菜单 —— 看起来像系统根本没听懂。老老实实回一句"车里没有薯条，现在有这些"才是对的。

findItemByName 用包含而不是相等：用户说「薯条」，车里叫「薯条（中）」；说「可乐」，车里叫「无糖可口可乐」—— 用户不会背全名。多条命中时取最短名字那条，保证同样说法每次命中同一项，确定性比"更聪明"重要。

05①.6 context：模糊意图旁路

新增LLM 判断产结论不产菜单llm-intent.service.ts:413 analyzeContext()

用户原话：「如果是模糊意图，比如说是很烦、今天心情不错，或者说给我点个午餐没有明确的，旁路根据用户知识（包括当下时间判断），判断结论导入主 loop。如果有明确意图，比如我要吃辣、3 个人 50 块这种，就不需要旁路，直接第二步。」

旁路的产物不是菜单，是一份判断结论：方向标签 + 推定人数 + 软预算 + 该避开的。由 applyContextToIntent 合并进 intent，再交给确定性选品引擎去真实菜单里落地。这样"模糊"就不会变成"再问一遍用户"，而是变成"系统替你多想了想"。

为什么旁路推的预算不能进 explicit.budget：

用户从没说过 87.5，却被系统按这个数当墙；而且模型每次推的数还不一样（实测同一句话推出过 87、88、87.5 三个版本），导致同一句输入每次得到不同菜单。软目标只能影响选品偏向，不能当硬指标。

第一轮的分档细节（本次修复的核心）

tierOf(p):                    // 0 最好
  serves === people  → 0        // 一份刚好够所有人吃
  serves >   people  → 1        // 一份有多，比如 2 人点三人餐
  serves >= 2        → 2        // 多人餐但一份不够，按 qtyOf 叠份数
  serves === 1       → 3        // 单人餐，只在凑不出多人餐时才用

overOf(p):                    // 按现有份数规则真会多出来几个人份
  serves < 2  → max(0, people − 1)
  else        → serves × qtyOf − people

排序：tier ↑ → over ↑ → serves ↓ → score ↓ → price ↑

同档内"超额人数少的优先 → 覆盖人数多的优先 → 分数高的优先 → 便宜的优先"。这条排序让「一份刚好够 3 人」的三人餐永远排在「3 份单人套餐」之前，与打分多少无关。

补配角的 60% 价格上限

为什么不能用「不超过主餐单价」这种绝对比较：补位环节会挑分数最高的那件，而"在你平时价位"这个 +1 分对小食也生效。于是 ¥55.9 的双人餐后面跟了一份 ¥39.9 的「麦麦炸鸡5拼」—— 两个人一餐 ¥118.3，跟三个人的 ¥122 几乎一样。而 ¥39.9 < ¥55.9 能轻松通过"不超过主餐"的检查。
改成 60% 比例：双人餐 ¥55.9 → 上限 ¥33.5（¥39.9 拼盘出局，¥15 麦乐鸡、¥13.5 新地都还在）；单套餐 ¥32 → 上限 ¥19.2，小食甜品全能进。没有主餐时（纯小食单）不限制，否则一件都选不出来。

15三人餐错误复盘（真实案例）

已修复这是这份文档里唯一一条"完整事故复盘"，因为它把选品引擎的两个结构性缺陷同时暴露了出来。

菜单上明明有「畅享吃鸡三人餐」，为什么没优先选它？

两个独立的根因（都不在打分权重上）

#缺陷后果
1 servesOf() 把"三人"并进了 return 4 三人餐被当成"够 4 人吃"，打分只给 +1；而单人套餐命中「应季·汉堡」拿 +3 —— 三人餐永远排不过单人套餐。份数按 ceil(3/4)=1 算、记账按 4 人份算，账面上"够吃"了，实际三个人只有一份套餐，于是又补 3 份单人套餐
2 isCombo() 白名单里没有裸的「N 人餐」 「畅享吃鸡三人餐」被判成单品：第一轮"整餐优先"收不到它、第二轮"补主食"认不出它（名字里没有堡/饭/卷/鸡块），最终从第三轮"补配角"混进来，被当成一份小食 —— 于是出现 3 个单人套餐 + 1 份三人餐 = 6 人份，账还按"够 4 人吃"记
为什么"调权重"救不了：分数是加权求和，节气关键词（+3）、口味（+4）这些项对单人套餐同样生效。一旦菜单里有个名字带"辣/甜/板烧"的单人套餐（+4），它 ×3 份就把三个人名额全占了。这不是权重没调好，而是两类商品根本不可比 —— "一份 3 人份的餐"和"3 份 1 人餐"在总价、剩菜、饮品份数上完全不同。所以最终做成结构优先级（tierOf），而不是继续在分数上加权重。

2 GAP数据来源角标恒为"实时" dataSource 初始化成 'mcp' 后再没被赋值。命中 TTL 缓存时前端仍显示"已实时核对门店菜单"，'cache' 分支永远走不到。缓存命中信息其实在网关的 CallMeta.cached 里，只是没往上传。 orchestrator.ts:309
3 GAP优惠券只是动画 拉了 available-coupons，有券就推一个 stage: coupon，但券从未参与算价。ChatReply.total 的注释写着"券后实付"，名不副实。 orchestrator.ts:554
4 GAP「换一换」不记得上一单 前端把输入框填成「换一批，别重复刚才的」再发一次，服务端没有任何"排除上一单"的逻辑（无 history 参数）。所以很可能推出同一份菜单 —— 文案承诺了做不到的事。 ChatView.vue:566 fillRefine
5 GAPknowledge stage 声明了但从不发 StageName 里有它、stage-texts.ts 里有 3 条文案，但 runChat 里没有这一行 —— 知识层是完全静默的。契约里 7 个 stage，实际最多只出现 6 个。 contract.ts:542 vs orchestrator.ts
6 GAPauto_confirm 存了没用 能读写、能在 /api/me 返回，但下单链路完全不读它 —— 永远要手动点"确认下单"。免确认一键下单实际未实现。 auth.service.ts:152
7 GAPsoftBudget 产出但没人消费 旁路把推出来的预算放进 intent.softBudget，但 SelectInput 没有这个字段，selectProducts 也不读它。所以"按你平时的价位配一单"这层意图实际不生效（注：这比让它进 explicit.budget 安全得多，但确实是空转）。 llm-intent.service.ts:615
8 GAP三个字段产出后无消费者 orderIntent（是否在表达"要点一单"）、moodConfidence（情绪置信度）、targetDate（明天/后天）都被解析出来并写进 ParsedIntent，但下游没有任何代码读它们。另外 needsClarify 在新架构下恒 false，实际已退役（反问改由 clarity + sideChannelEmpty 决定）。 contract.ts:315/327
9 GAP访客先烧两次 LLM 才被告知没登录 访客会先跑 intent（1 次 LLM）、模糊时再跑 context（第 2 次 LLM）、跑到 menu 层才遇到 NEED_LOGIN 终止。视觉上像"想了半天才告诉我没登录"，实际还白烧了模型额度。登录检查可以前置到流水线第一行。 orchestrator.ts:317
10 GAP外送划线价会被覆盖两次 priceDelivery() 把 calculate-price 的 original（含配送费口径）写进 originalTotal，随后 originalTotal = finalTotals.original 又用商品原价合计覆盖一次。只影响"原价 ¥xx"的划线展示，不影响实付。 orchestrator.ts:582 / 644
11 GAP旁路"读心结论"到不了文案层 contextRead（"ta 大概是加班到现在，想吃口热的"）只传给了复核环节，buildUserPrompt 不读它。所以旁路想清楚的事，最终说不出那句最该说的话 —— 这恰恰是"懂你"值钱的地方。 menu-review.service.ts:270
另外三个"不是问题但要知道"的点：
① 标题/文案里的节气、星座、水逆全部由静态数据表 + 纯函数算出（data/solar-terms.ts 等），不联网、不调模型，所以演示绝不会因为网络或模型抽风而变样。
② 到店菜单走了 TTL 缓存（10 分钟），同一门店连续问同一句话，第二次的 MCP 调用几乎为 0，但用户看到的价格仍是 10 分钟内的真实数据。
③ MCP 目录里共 35 个工具、6 个分组（定位门店 / 菜单选品 / 优惠券 / 点餐交易 / 积分商城 / 活动派对），其中 7 个写操作永不缓存且必须显式确认。产品链路（对话 + 下单）只用到其中 11 个：query-meals / query-nearby-stores / available-coupons / list-nutrition-foods / delivery-query-addresses / delivery-query-stores / delivery-create-address / calculate-price / create-order / query-order / cancel-order；其余 24 个通过 /api/explorer 的 21 个端点暴露成数据浏览面板。

一句话总结现状

这条 loop 的"想"和"算"是完全确定的（规则 + 静态知识 + 真实 MCP 数据 + 可复现打分 + 一道算术体检），"判断"交给模型但有边界（clarity 和 review 两处，都没有选品权），"说"才完全交给模型。它能保证不编价格、不编菜单、不越权下单、不把 3 个人喂成 6 人份；目前欠的是券真正参与算价（#3）、换一换的记忆（#4）、旁路结论到不了文案层（#11）和角标诚实度（#2）—— 这四件事都不影响"能点成一单"，只影响"聊得像不像人"和"省钱感"。
